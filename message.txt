Часть 3. Банк идей и гипотез для разработки
Ниже собраны гипотезы, разделенные по уровням архитектуры системы.

Слой A. Универсальный Grounding (поиск точки входа по тексту)
Гипотеза 1: Автоматическое извлечение OpenAPI/REST-спецификации из AST.

Суть: Вместо regex анализатор автоматически сканирует аннотации Spring MVC (@RestController, @RequestMapping, @GetMapping, @PostMapping, @PathVariable). Для каждого эндпоинта формируется универсальный профиль: HTTP метод, URL-паттерн, типы параметров DTO, JavaDoc/комментарии, название метода и класса.

Польза: Полная независимость от предметной области; работает на любом Spring Boot проекте.

Гипотеза 2: Cross-Encoder / Двунаправленный семантический матчинг (Zero-Shot).

Суть: Векторизовать текст шага сценария (например, "passenger buys a ticket without food") и сопоставить его с семантическим описанием эндпоинтов (через локальные легковесные sentence-transformers или BM25 по расширенным синонимам WordNet). Метод с наибольшей косинусной близостью выбирается как входной.

Гипотеза 3: Трассировка графа интерфейса (UI-to-Backend Flow Mining).

Суть: В веб-проектах фронтенд связывает кнопки пользователя с API. Анализатор парсит JavaScript/HTML (теги <button>, обработчики onclick, вызовы fetch, axios.post('/api/...')). Текст шага матчится на UI-элементы, а от них автоматически восстанавливается путь к шлюзу и микросервису без ручных правил.

Гипотеза 4: Subject-Verb-Object (SVO) семантический парсинг шага.

Суть: Использование NLP dependency parsing (spacy/nltk): извлекаются глагол действия (action: create, cancel, pay, view) и объект (entity: user, contact, payment, luggage). Далее ищется метод контроллера, чьи леммы имени метода и класса максимально близки к полученным (verb, noun).

Слой B. Универсальное извлечение параметров и связывание данных
Гипотеза 5: Type-Driven Slot Filling по структуре DTO.

Суть: Если найден метод контроллера, анализатор берет сигнатуру его аргументов (например, класс OrderInfo). Через AST инспектируются поля класса: типы данных, аннотации валидации (@NotNull, @Min). Текст сценария сканируется на наличие соответствующих типов: даты (ISO-формат), числа, денежные суммы, флаги (да/нет). Заполнение полей DTO происходит по типам и семантической близости имен полей.

Гипотеза 6: Автоматический парсинг Enum-констант проекта.

Суть: Анализатор находит все enum в проекте. Для любого слова или фразы из сценария ищется ближайшее имя константы Enum во всем проекте (например, "first class" → SeatClass.FIRSTCLASS). Никакие конкретные имена классов и enum не зашиваются в код.

Гипотеза 7: Автоматическое разрешение контекста отрицания (Negative Polarity Context).

Суть: Обобщенный алгоритм для выявления отрицаний в предложении ("without insurance", "do not select meals", "refuse luggage"). Если поле DTO или сущность найдена в зоне действия отрицания, ему присваивается null, 0 или false.

Слой C. Универсальный движок исполнения (Execution & State Engine)
Гипотеза 8: Обобщенная сущностная машина состояний (Generic Session State Machine).

Суть: Сейчас в коде жестко прописано state.orders, state.contacts. Вместо этого вводится универсальный реестр типов SessionContext[EntityClass].

Как работает: Когда любой сервис сохраняет объект в БД (вызов метода репозитория save(...)) или возвращает JSON с id, анализатор автоматически сохраняет этот объект в SessionContext под ключом его типа (User, Contact, Order и т.д.). Когда следующий шаг требует id сущности типа T, движок автоматически берет последнюю созданную сущность типа T.

Гипотеза 9: Анализ потока управления (CFG) с интервальным / символьным исполнением.

Суть: Построение графа потока управления (Control Flow Graph) для Java-метода через дерево разбора AST.

Разрешение условий:

Если переменная в if (condition) известна из параметров или БД → исполняется строго активная ветка;

Если значение Unknown → применяется эвристика наиболее вероятного пути (Happy Path по умолчанию, либо ветка без выброса throw Exception / return Error).

Гипотеза 10: Автоматическое связывание межсервисных вызовов (RPC / REST Routing).

Суть: Когда метод вызывает restTemplate.postForObject("http://ts-order-service/api/...", ...):

Движок статически извлекает URL;

По скелету или конфигам шлюза (application.yml) разрешает имя целевого сервиса и путь;

Находит соответствующий @PostMapping в целевом сервисе и добавляет ребро remote полностью автоматически.

Гипотеза 11: Анализ метаданных JPA / Hibernate для связей data.

Суть: Связь data должна вести от метода, вызывающего репозиторий, к таблице БД. Вместо хардкода таблиц движок анализирует:

Наследование от CrudRepository<EntityType, ID> или JpaRepository;

Аннотацию @Table(name = "...") у EntityType;

Аннотации @CollectionTable, @OneToMany, @ManyToMany для каскадных таблиц.

Это гарантирует 100% точность предсказания data-связей для любого Spring Data проекта.

Слой D. Обобщенная фильтрация и проекция графа (Graph Pruning & Projection)
Гипотеза 12: Анализ чистоты методов (Purity / Side-Effect Static Analysis).

Суть: В решении № 5 фильтрация конструкторов была захардкожена под 3 класса. В обобщенном виде строится классификатор побочных эффектов:

Метод/конструктор считается тривиальным аксессором, если он не совершает вызовов других методов, не пишет в БД, не бросает исключений и лишь перекладывает аргументы в поля.

На основе конфигурации фреймворка такие вспомогательные узлы системно исключаются из результирующего ответа.

Гипотеза 13: Вычисление срезов программы (Program Slicing) от внешних эффектов.

Суть: Граф обхода строится только по тем путям, которые имеют внешние эффекты: обращение к БД (data), вызовы других микросервисов (remote) или формирование HTTP-ответа. «Мертвые» ветки и утилитарные методы отсекаются алгоритмически.
