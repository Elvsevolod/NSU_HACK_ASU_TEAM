# Правила хакатона и наши принципы

**Единственный источник правил.** Всё остальное в папке на этот файл ссылается, а не пересказывает. Выжимка из `tt-challenge/README.md` и `tt-challenge/REFERENCE.md` плюс наши ограничения. Первоисточники — в конце.

## 1. Задача

По текстовому описанию действий пользователя, исходникам проекта и предварительному графу-скелету **предсказать, какие методы выполнятся, какие вызовы и межсервисные обращения произойдут и к каким таблицам обратится код — без запуска Train Ticket**. Учитывать входные данные, начальное состояние системы и последствия предыдущих шагов.

## 2. Формат ответа

- **Один JSON на все сценарии**: поле `project` и словарь `scenarios`, ключ — ID сценария, значение — блок с `edges`.
- Каждое ребро: `source`, `relation`, `target`. В скелете вид связи в поле `type`, в нашем ответе — `relation`.
- `relation` — один из четырёх: `executes` (сценарий → метод), `calls` (метод → метод), `remote` (метод → метод другого сервиса), `data` (метод → таблица).
- Концы рёбер — **существующие ID из `nodes`**; сокращения не принимаются. `scenario:S0` — служебный ID, его нет в скелете.
- Новые вершины и исполняемые строки добавлять нельзя. Ответ описывает весь сценарий: порядок и повторы не нужны, одинаковое ребро — один раз.

## 3. Как оценивают

- Для каждого вида связи ответ — **множество рёбер**. Балл вида = `|совпало| / |объединение|` (IoU, коэффициент Жаккара).
- **Лишние рёбра снижают балл так же, как пропущенные.**
- Балл сценария — среднее по четырём видам. Итог — среднее по **семи скрытым** сценариям. Открытый **S0 в итог не входит**.
- Если у нас и в эталоне рёбер вида нет — за вид **1**; если в эталоне пусто, а мы добавили — **0**. Нет блока сценария — за него **0**.
- **Локально** по скрытым S1–S7 можно проверить только **формат** (существование ID, виды вершин, отношения), потому что эталон скрыт. **На сайте** эти же сценарии оцениваются по существу. «Проверка формата проходит» не значит «ответ правильный».
- **Надбавка за Rust**: ×1,10 (не выше 1,0), после проверки сданного кода. Тонкая обёртка над другим языком надбавку не получает.

## 4. Что можно и что нельзя

**Можно:** читать и компилировать исходники, применять статический анализ, текстовый поиск и модели машинного обучения; учиться на открытом S0 (`gold/S0.json`, `context/`).

**Нельзя:** запускать Train Ticket или его отдельные сервисы, собирать трассы исполнения, использовать самостоятельно собранные рантайм-данные.

**Наши дополнительные запреты:** не изменять `tt-challenge/`, `sample/` и прежние `runs/`; работать только в `solutions_G/`; не импортировать изменяемый код другого варианта — код родителя копируется снимком.

## 5. Наши обязательные ограничения

- **Язык: только Python.** Все варианты пишутся строго на Python. Единственное исключение — **самый последний итоговый (заключительный) вариант**: он пишется на Rust ради надбавки +10% и не должен менять сам ответ, если не сказано иное. Внешние LLM API запрещены на любом этапе.
- **Эталон используется только проверкой**, но не построителем ответа.
- **Не добавлять поведение по идентификаторам S0–S7** и готовые рёбра под конкретный сценарий.
- Оценка сайта и локальный S0 — разные показатели; в имя папки идёт только оценка сайта.

## 6. Принципы качества (главное для чатов)

1. **Не хардкодить под сценарий.** Запрещено: поведение, зависящее от ID сценария (S0–S7); готовые рёбра из эталона; подстановка частного случая вместо общего правила.
2. **Доменную специфику изолируем в профиль.** Это не противоречие правилу 1. Названия таблиц, сущностей, эндпоинтов, дефолты, лексикон проекта — **допустимы и необходимы**: без них анализ конкретного проекта невозможен. Требование одно — собрать их в одном явном месте (`profile.py`) и применять по общему правилу, а ядро держать независимым от них. «Хардкод сценария» и «знание о проекте в профиле» — разные вещи: первое запрещено, второе разрешено.
3. **Одно изменение — один вариант.**
4. **Рефактор не меняет вывод.** Структурные изменения обязаны давать ответ **байт-в-байт** как родитель и не сдвигать S0.
5. **Точность важнее полноты.** Из-за IoU удаление лишнего ребра ценно так же, как добавление нужного; переусердствовать с удалением тоже нельзя.
6. **Оценка сайта — только по факту.** Никогда не вычисляем и не прогнозируем балл сайта; ставим его только из предоставленного скриншота.
7. **S0 — страховка, не индикатор прогресса.** Он узкий (по `REFERENCE.md`: `0 remote`, только вход/контакты/заказы/багаж) и нужен лишь для проверки, что ответ не сломался. У линии № 5 он держится на 0,9260149573; у другого родителя или корневого варианта будет своё значение. Роста от S0 не ждём.
8. **Не привязываться к одному решению.** Общий № 5 (score сайта 0,909870) — ориентир по баллу, но **не обязательная основа**. Вариант можно строить на другой идее или другом коде — в том числе с нуля: корневой вариант без родителя допустим.

## 7. Критерии приёмки изменения

- Структурное изменение: ответ совпадает с родителем **побайтово**, S0 не сдвинулся, тесты зелёные.
- Изменяющее ответ: новый вариант, новый `submission.json`, локальный S0 и формат-чек, README с бенчмарком. Оценка сайта — отдельно, только после скриншота.
- Корневой вариант (без родителя): критерий тот же, что у изменяющего ответ; побайтово сверять не с чем.
- Любой вариант ведётся по правилам `skills/solution-versions/SKILL.md`; проверка — по `skills/s0-check`, сборка посылки — по `skills/submission-pack`.
