# Решение № 4 — identity-contact-payment

Родитель — решение № 3, `stateful-response-propagation`, score сайта **0,886660**. Score сайта решения № 4 — **0,907050**, по скриншоту пользователя от 16.10.2026. Прирост — **+0,020390**. Оценённый архив [solution.zip](solution.zip) сохранён без изменений; в его корне находится [submission.json](submission.json) с ответами на **S0–S7**.

## Фича

Исправлена цепочка регистрации, создания контакта и оплаты для нового пассажира; уточнены выбор пассажира и выбор заказа при двух покупках. Это продолжение статического анализатора на Python: он разбирает Java-код и моделирует значения и изменения данных в памяти. Train Ticket, JVM и базы данных не запускаются, внешние LLM API не используются. Эталон читает только отдельный оценщик.

Изменения относительно № 3:

- Добавлена обработка простых Lombok-builder и конструкторов `@AllArgsConstructor` по полям исходного класса. Учтены строковые константы и цепочка `ResponseEntity.status(...).body(...)`. Благодаря этому результат регистрации содержит ID нового пользователя, который передаётся в авторизацию, контакт и заказ.
- Для неуказанных полей нового пользователя и контакта создаются различные символические значения. Записи сохраняются только через разобранные вызовы репозитория; повторное создание с теми же данными может закончиться отказом по коду приложения.
- Раздельно сохраняются существующие и новые контакты. «Первый контакт» и «новый контакт» больше не превращаются в одного пассажира; «первый новый заказ» и «второй новый заказ» выбирают разные покупки.
- Оплата начинается с `inside-payment`, как в интерфейсе бронирования. Этот сервис проверяет баланс и при необходимости вызывает `payment`; только успешный ответ позволяет изменить статус заказа на оплаченный.
- Обрабатываются `Enum.values()` и поля, присвоенные аргументами конструктора enum. Тип страховки получает правильные `index`, `name` и `price`, после чего достигается создание страховки. Составной ключ `TripId` сравнивается по значению enum, независимо от полноты загруженных полей.
- Названия станций передаются из выбранного результата поиска, как в интерфейсе покупки. Меню возвращает еду для поезда, выбранная позиция передаётся в заказ. Фильтр `'Cancel'` включает проверку статуса отменённых заказов.

Правила не зависят от ID S0–S7 и не содержат готовых рёбер эталона. Их независимость от ID проверена переименованием сценариев. Языковой адаптер при этом остаётся ориентированным на Train Ticket.

## Что исправлено в S4

В № 3 регистрация теряла значения builder, из-за чего личность нового пассажира оставалась неизвестной. Оплата выбирала внешний сервис напрямую: пропускались проверка баланса, внутренняя запись платежа и установка статуса заказа. Это мешало последующим шагам отмены и возврата.

В № 4 ID созданного пользователя совпадает с ID после входа и владельцем нового контакта и заказа. У нового пользователя нет пополнений баланса. При оплате исходный код проходит через `inside-payment`, вызывает внешний `payment` и переводит заказ в статус `1`. Расчёт возврата даёт `40.00` для билета ценой `50`; отмена переводит заказ в статус `4`, а последний запрос возвращает отменённый заказ. Вся последовательность статусов: **`0 → 1 → 4`**.

В меню определяется первая позиция на борту поезда; её название и цена доходят до бронирования. Создание страховки тоже проходит успешную ветку. Дополнительно проверено: при достаточном балансе внешнего вызова нет, а при отказе внешней оплаты заказ остаётся неоплаченным.

## Что исправлено в S3

Первый билет оформляется на первый существующий контакт, второй — на только что добавленного спутника. У заказов разные ID, документы пассажиров и классы мест: первый и второй класс соответственно. Просмотр «первого нового заказа» и «второго нового заказа» выбирает нужную запись. Оба заказа отдельно оплачиваются с внутреннего баланса.

Исправлено получение типа страховки: индекс `1`, название `Traffic Accident Assurance`, цена `3.0`. Создание страховки теперь достигает её конструктора.

**Изменение итогового графа S3 небольшое:** добавлены один исполнившийся метод и один вызов конструктора страховки. Выбор другого контакта или заказа меняет значения без изменения множества методов. По результату сайта улучшения состояния не дали прироста S3: оценка снизилась с **0,885 до 0,883**. Разбор двух добавленных связей приведён ниже.

## Разбор результата сайта

**S4: 0,763 → 0,911, рост на 0,148.** Это единственный сценарий с ростом оценки, и он обеспечил повышение общего результата. В № 3 неопределённость после регистрации переходила в контакт и заказ; оплата выбирала внешний сервис напрямую, а возврат и отмена завершались `Order Not Found`. В № 4 новая личность и созданный заказ известны, поэтому дальнейшие условия проверяются по их значениям.

| Этап S4 | Статическая модель № 3 | Статическая модель № 4 |
| --- | --- | --- |
| Регистрация и контакт | Результаты неизвестны | Новый пользователь и его контакт созданы |
| Меню | `Get All Food Failed` | `Get All Food Success`, выбрана еда на борту |
| Список и открытие заказа | Данные заказа неизвестны | Возвращается один заказ нового пользователя |
| Оплата | Прямой вход во внешний payment; статус ответа неизвестен | inside-payment → payment → изменение статуса заказа |
| Расчёт возврата | `Order Not Found` | `40.00` для цены `50` |
| Отмена и фильтр | Отмена отклонена, результат списка неизвестен | Заказ получает статус `4` и возвращается фильтром Cancel |

На шаге оплаты число межсервисных рёбер выросло с 0 до 3, при отмене — с 2 до 4. При этом удалились обращения к order-other, которые не нужны для известного скоростного поезда. Рост оценки согласуется с восстановлением этих цепочек. Скрытого эталона и оценок отдельных изменений нет, поэтому нельзя разложить +0,148 по регистрации, оплате, возврату и остальным правкам. Оставшаяся разница с единицей также не показывает, какие именно связи ещё неверны.

**S3: 0,885 → 0,883, снижение на 0,002.** Ошибки состояния устранены: в № 3 оба открытия «нового заказа» выбирали один и тот же заказ, а добавление контакта оставалось неопределённым; в № 4 открываются две разные покупки для разных пассажиров. Но платформа оценивает множество методов и связей за весь сценарий. Значения ID, имена пассажиров, порядок и число повторений в эту метрику не входят. Поэтому эти исправления почти не затронули отправляемый граф.

Точное сравнение JSON показывает только два добавления в S3:

1. `executes`: `Assurance.<init>(String, String, AssuranceType)`.
2. `calls`: `AssuranceServiceImpl.create(...) → Assurance.<init>(String, String, AssuranceType)`.

Удалений и других добавлений нет. **У S1 добавлена ровно та же пара, и оценка тоже снизилась на 0,002.** При неизменном эталоне снижение обоих сценариев локализуется до этой пары. Это сильный признак лишних для оцениваемого графа связей, но состав скрытого эталона непосредственно недоступен. Результат не означает, что исправления контактов и заказов ошибочны.

В Java-исходнике `AssuranceServiceImpl.create` действительно явно вызывает этот конструктор при отсутствии существующей страховки и корректном типе. Следующая проверка должна выяснить, почему данная ветка или учёт её конструктора расходятся с оценкой. Автоматически исключать все конструкторы или вводить исключения по ID S1/S3 было бы необоснованно. Нужна проверка общей семантики вызовов и пути создания страховки; при необходимости — уточнение правил учёта у организаторов.

**S2, S5, S6 и S7:** оценки не изменились, и множества рёбер полностью совпадают с № 3. Это подтверждает отсутствие изменений ответа для этих сценариев. S6 сохраняет наибольший балл, **0,923**, затем S7 — **0,921**. Теперь самые слабые — **S3 (0,883)** и **S2 (0,889)**; S4 поднялся до уровня S1 и S5.

Для следующей итерации стоит сохранить изменения регистрации и оплаты S4, сначала разобрать общую пару связей страховки в S1/S3, затем оставшиеся расхождения S3 и S2. В текущем решении записаны только метрики и анализ: код и отправленный ответ не менялись.

## Проверки и ограничения

Проверены исходные S0–S7, независимость от ID, два разных пассажира и заказа, перенос нового пользователя, страховка, еда, оплата, отмена, повторная регистрация и дублирующий контакт. Проверки оплаты меняют баланс и результат внешнего сервиса. Сохранены проверки S2, S5, S6 и S7 из № 3. Во время интеграционных тестов доступ к сети и чтение `gold` запрещены; исходный дамп после анализа не изменяется.

Анализатор не является полным интерпретатором Java или универсальной системой для любого проекта. Не все stream/lambda-операции поддерживаются: например, карта станционных магазинов в меню S4 частично остаётся `Unknown`, хотя еда на борту определена. Некоторые номера мест и токены тоже неизвестны. Шифрование паролей и инфраструктурная авторизация представлены абстрактными моделями; реальной проверки учётных данных нет. Модели Lombok покрывают используемые простые конструкции, но не все возможности библиотеки.

Сценарии не задают точные значения полей регистрации и нового контакта. Здесь используются представители новых значений, отличные от данных дампа; это явно принятое допущение для успешного ввода. Контекст времени и дамп те же, что в № 3. Дополнительные скрытые условия могут потребовать уточнения модели.

## Запуск

Команды выполняются из папки этого решения. После переноса укажите свои пути к исходному пакету организаторов; переименование папки решения запуск не ломает.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
PYTHONHASHSEED=0 PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B code/run.py \
  --source ../../tt-challenge/targets/trainticket \
  --skeleton ../../tt-challenge/skeleton/trainticket.json.gz \
  --context ../../tt-challenge/context \
  --scenarios ../../tt-challenge/scenarios \
  --output submission.json \
  --report benchmark/analysis-report.json
```

Отдельная оценка S0 и проверка формата:

```bash
.venv/bin/python -B ../../tt-challenge/platform/evaluate_golden.py \
  ../../tt-challenge/gold/S0.json submission.json --json
.venv/bin/python -B ../../tt-challenge/platform/evaluate_golden.py \
  --check ../../tt-challenge/skeleton/trainticket.json.gz submission.json --json
```

Код возврата `3` второй команды означает `format_only`: формат проверен, оценка без эталона не вычисляется.

Для тестов дополнительно нужен `pytest==9.1.1`. Если исходные данные лежат в другом месте, задайте `TT_CHALLENGE_ROOT` абсолютным путём к `tt-challenge`.

```bash
.venv/bin/python -m pip install pytest==9.1.1
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=code .venv/bin/python -B -m pytest code/tests -q -p no:cacheprovider
```
