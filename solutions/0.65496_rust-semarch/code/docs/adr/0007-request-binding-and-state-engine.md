# ADR 0007 — Привязка запроса и движок состояний сценария (N05/N06)

* Статус: Accepted
* Дата: 2026-10-18
* Связан: ADR 0003 (механизмы разрешения), ADR 0005 (привязка входа к шагу),
  ADR 0006 (упорядоченный IR и анализ значений)

## Контекст

ADR 0006 дал ядру упорядоченный IR и анализ значений: для тела метода теперь
можно ответить на вопрос «что выполнится, если параметры имеют такие-то
значения». Но параметры берутся не из воздуха. Сценарий описывает действия
пользователя словами; чтобы анализ значений что-то решил, слова должны стать
**полями запроса**: `verifyCode` в `TokenServiceImpl#getToken` появляется
только потому, что запрос логина его принёс.

До этого инкремента ответ строился одним механизмом — `TtGraph::predict`:
объединение выбранных входов, обход графа вызовов по скелету, отсечение мест
вызова по *словам сценария* (G6). Он честно отвечает на вопрос «какой подграф
достижим», но не различает:

* «в запросе есть код» и «в запросе кода нет» — оба одинаково достижимы;
* «обработчик прочитал поле» и «обработчик прочитал `null`»;
* «ветка пройдена, потому что так сказал пользователь» и «ветка пройдена,
  потому что мы не знаем значения».

Ограничения решения:

1. Ответ конкурса не имеет права измениться: старый путь остаётся основным.
2. `unknown != false`: молчание сценария о поле — это не отсутствие поля.
3. Ни одного правила, зависящего от имён Train Ticket: и словарь полей, и
   типы берутся из данных проекта (скелета), а правила вывода — из семантики
   языка и публичных контрактов (JavaBeans-доступ, `StringUtils.isEmpty`).
4. Никакой таблицы «сценарий → значение». Допустим только адаптер формата.
5. Генеральная пригодность: механизм обязан работать на переименованном
   проекте (generality-gate).

## Решение

### 1. Привязка запроса (`tt/src/request.rs`)

`BoundRequest { step, endpoint, method, fields, unmatched, gaps }`,
`BoundField { name, declared, value, origin, provenance }` — на каждое
объявленное поле запроса-типа обработчика. Словарь полей и их объявленные типы
читаются из скелета (`field`-узлы: имя + `type`/`type_raw`); за кадром
остаются только «рамочные» типы (`java.`, `javax.`, `jakarta.`,
`org.springframework.`), потому что это параметры HTTP, а не тело запроса.

Значение поля — одно из четырёх, и это ядро решения:

| значение | что означает | доказательство |
|---|---|---|
| `Literal(v)` | сценарий называет значение | фраза payload-клаузы |
| `Empty` | сценарий говорит «пусто» | `empty`/`blank` перед упоминанием поля |
| `Absent` | сценарий говорит «не отправлено» | `without`/`no`/`missing`/… перед полем |
| `Unknown` | сценарий о поле молчит | отсутствие упоминания |

`Unknown` **никогда** не превращается в «поля нет»: молчание сценария не
утверждение о теле запроса. Это же правило определяет, что в `Env` попадает:
только типизированное значение (`Absent` для ссылочного типа — это `Null`,
для примитива — по-прежнему `Unknown`, потому что примитив не может
отсутствовать, и подстановка нуля была бы выдумкой).

Provenance есть у каждого поля: какая клауза, какая опция или какое молчание
его решили. Слова payload, не назвавшие ни одного объявленного поля, попадают в
`unmatched` (переименованное поле DTO — это факт, а не поле, куда можно
догадаться).

### 2. Статические значения UI (`tt/src/ui.rs::extract_options`)

`<select>`/`<option>` со статическими значениями — это значения, которые
интерфейс *действительно* может отправить, поэтому они участвуют в привязке:
опция связывается с полем, когда управляющий элемент носит это поле, **и**
слова шага называют метку опции. Обе половины обязательны: наличие опции в
списке не является утверждением, что пользователь её выбрал, а метка в прозе
без элемента, несущего поле, — значение, которое обработчик не может получить.
Шаблонные списки (`value="{{item.value}}"`) отбрасываются: их значение —
выражение JavaScript, а не значение.

Отсюда — честный результат для типов страхования Train Ticket: список
подтягивается в рантайме (`/assurance/getAllAssuranceType`), статических
`<option>` в исходниках нет, поэтому поле остаётся `Unknown` с
провенансом «значения нет в исходниках», а не выдуманным `0`.

### 3. Читатели (`core/src/{value.rs,analysis.rs}`)

`LanguageProfile::bean_accessors()` — профиль языка решает, работает ли
конвенция JavaBeans (`getVerificationCode()` → свойство `verificationCode`).
Правило срабатывает **только** на квалифицированном ключе `<receiver>.<field>`,
который засеял движок, поэтому случайный `getPrice()` у локальной переменной не
подхватит поле запроса с тем же именем.

`StringUtils.isEmpty(null)` → `true` — это публичный контракт Spring
(`Object`-перегрузка проверяет и `null`, и `""`), а не догадка о проекте.

`BodyAnalysis.decisions: Vec<GuardDecision>` — каждое решение ветки с
вердиктом, символами условия и путём-свидетелем. Это и есть «доказательство»:
из «удалённого ребра» оно делает «ветка доказана ложной на этом пути».

### 4. Межпроцедурная передача значений (`tt/src/engine.rs`)

Объект передаётся по ссылке-дескриптору: если фактический аргумент — символ,
привязанные свойства переменной вызывающего переезжают под имя параметра
вызываемого (`dto.verificationCode` → `param.verificationCode`). Это семантика
передачи объекта, а не знание о проекте. Копии значений (чтение поля в
примитив, значение, возвращённое помощником) пока не переносятся, и это
записано как граница, а не как молчаливое «наверное, ничего».

### 5. Движок сценария (`tt/src/engine.rs`)

Режимы: `legacy` (ответ конкурса, без изменений), `shadow` (ответ конкурса
плюс записанный дифф), `semantic` (ответ движка). Шаг за шагом:

1. привязка шага к обработчику (ADR 0005) и к его запросу;
2. анализ тела обработчика по упорядоченному CFG (`analyze_body`) с засеянным
   `Env`;
3. каждое **достигнутое** место вызова отдаёт свои рёбра
   (`TtGraph::edges_of`) вместе с вердиктами охран как доказательством;
4. целевые методы посещаются с привязкой аргументов; объединение — **только
   после последнего шага**, поэтому `StepOutcome` каждого шага независим и
   слова позднего шага не переписывают ранний.

Два предохранителя:

* **Отсечение — это доказательство.** Если тело понижено с *любым* пробелом,
  значение-отсечение для этого метода выключается, и все его места вызова
  остаются живыми (как в legacy). Недоказуемое ребро честнее «доказанного».
* **Ограничения записываются.** Нет пониженного тела, места вызова нет в IR,
  исчерпан бюджет, аргументы не передались — каждая причина попадает в
  `gaps`/`suppressed` конкретного шага.

G6 (лексическое отсечение по словам сценария) в этом пути **не** применяется:
ветку решает значение, а не лексика. Это единственное систематическое
расхождение с legacy, и оно печатается в дифф с точной причиной.

### 6. Тень вместо подмены

`--mode shadow` печатает ответ legacy (побайтово тот же) и пишет отдельный
диффф: `only_legacy`, `only_semantic`, `only_legacy_executes`,
`only_semantic_executes`, `agreed`, `notes`, где у каждого ребра есть
объяснение (какое решение значения его убило; какой признак сценария его
отсекал у legacy). Так движок проверяется, не трогая сдаваемый артефакт.

## Следствия

* Ответ конкурса не изменился: `sha256 ea3c7ca2…` до и после инкремента.
* Движок воспроизводит legacy **точно** и добавляет только то, что legacy
  отсекал по словам: `only_legacy = 0`, `only_legacy_executes = 0` во всех
  сценариях, `only_semantic = 5` (4 вызова + 1 удалённый вызов
  verification-code сервиса).
* Вертикаль `verifyCode` проходит целиком: проза → поле DTO → аксессор →
  локальная переменная → охрана → ребро, с доказательством; при заданном коде
  ребро `remote` подтверждено, при молчании — возможно, при «пусто»/«без
  кода» — исключено.
* Незакрытые границы названы и вынесены: копии значений через аргументы,
  куча/поля объекта, значения перечислений, места вызова, которых нет в
  плоских фактах (тернарные плечи в `return`).
