# ADR 0006 — Упорядоченный IR и анализ значений (N03/N04)

* Статус: Accepted
* Дата: 2026-10-18
* Связан: ADR 0001 (граница стека), ADR 0003 (механизмы разрешения),
  ADR 0004 (граница ML/LLM), ADR 0005 (привязка входа к шагу)

## Контекст

Конкурсный ответ строится из «плоского» контракта фактов: методы, места вызова,
охраны, аннотации. Такой контракт отвечает на вопрос «что может произойти», но не
на вопрос «при каких значениях это произойдёт». Текущий путь (`TtGraph::predict`:
объединение входов, достижимость по скелету, глобальные текстовые признаки)
работает именно на этом контракте, поэтому он не умеет опереться на порядок
операторов, на условие `x == null` или на то, что `verifyCode` пришёл в запросе.

План (`research/06_ARCHITECTURE_DECISION.md`, стратегия C) требует сохранить
Rust-проект, Tree-sitter, индексы скелета, канонические ID, извлечение
кандидатов, экспорт и цикл измерений, но добавить поверх настоящий пошаговый
движок значений и состояний. Этот инкремент — первый шаг: **модель выполнения**,
на которую сможет опереться N05/N06 (привязка запроса, `StepOutcome`, вертикаль
`verifyCode`).

Ограничения, которые определили решение:

1. Анализ и построение ответа обязаны быть настоящим Rust (бонус ×1.10).
2. Ядро не должно знать про AST: иначе Tree-sitter протекает в анализ и
   переносимость на другой язык/стек становится фикцией.
3. `unknown != false`: незнание не должно превращаться в утверждение.
4. Никакой зависимости от идентификаторов сценариев, сущностей, таблиц и
   сервисов; правило должно выводиться из семантики языка, публичного контракта
   фреймворка или данных проекта.
5. Инкремент N03/N04 **не имеет права изменить конкурсный ответ**.

## Решение

### 1. Упорядоченный IR в ядре (`core/src/ir.rs`)

`FunctionBody = { entry, blocks: Vec<BasicBlock>, guards, exits, gaps }`,
`BasicBlock = { id, statements, terminator, span }`,

```text
Statement  = Assign { target, value } | Eval { value } | Unsupported { reason, detail }
Terminator = Goto { next } | Branch { guard, condition, then_block, else_block }
           | Return { value } | Throw { value } | Unreachable | Gap { reason, detail }
```

Терминатор `Gap` — это не «дырка в графе», а явное ребро: блок исполняется, но
порядок дальнейших шагов не моделируется (`switch`, `break` без учёта меток).
Поэтому эффекты за ним остаются `Possible`, а не исчезают.

`ValueExpr` остаётся **синтаксисом** (литерал, имя, поле, вызов, унарная/бинарная
операция, `Parameter{index}`), а `AbstractValue` — **доменом значений**. Это
разделение принципиально: синтаксис приходит из фронтенда, домен принадлежит
анализу, и подмена одного другим невозможна по типам.

### 2. Фронтенды понижают, а не анализируют (`frontend-*/src/lowering.rs`)

Java и Python понижают свои конструкции в один и тот же IR. Фронтенд не
вычисляет значений и не решает условий — он только расставляет блоки, порядок и
охраны. Всё, что он не умеет, становится `AnalysisGap` с причиной и диапазоном,
а не молчаливым пропуском.

Ключевое правило: **понижение не регистрирует новых мест вызова**. Плоский обход
(`walk`) остаётся единственным источником `ParsedFile.callsites`; понижение
находит место вызова по диапазону. Благодаря этому конкурсный набор фактов не
меняется, и `submission.json` побайтово прежний.

### 3. Домен значений (`core/src/value.rs`)

```text
AbstractValue = Unreachable | Unknown | Null | Bool | Int(i64) | Float(f64) | Str
```

* `Unknown` — top (нет информации), `Unreachable` — bottom (сюда нет пути).
  `join` возвращает конкретное значение при совпадении, второй операнд при
  `Unreachable`, иначе `Unknown`. Решётка ассоциативна, коммутативна и монотонна.
* Целые считаются точно в `i64` (`1 + 1 == 2`, `2^53 + 1 != 2^53`); переполнение,
  деление на ноль и упорядочивание не-чисел не выдумывают значение, а возвращают
  причину (`integer_overflow`, `integer_division_by_zero`, `ordering_of_non_number`),
  которую вызывающий превращает в `AnalysisGap`.
* Там, где языки действительно расходятся, решение принимает
  `LanguageProfile`, а не догадка:
  * `division_is_integral` — `7/2` это `3` в Java/Go/C#, но `3.5` в Python/JS;
  * `%` при разных знаках операндов не вычисляется вообще
    (`remainder_sign_differs_between_languages`): в Java остаток следует за
    делимым, в Python — за делителем;
  * `falsy_values_decide` — `if (0)`/`if ("")`/`if (None)` это ошибка
    компиляции в Java и ложь в Python;
  * `logical_yields_operand` — `&&`/`||` возвращают `bool` в Java и операнд в
    Python (`0 and f()` — это `0`, а не `False`);
  * `not` всегда даёт `bool` в Python и `Unknown` для не-bool в Java.

### 4. Анализ тела (`core/src/analysis.rs`)

Обход — рабочий список по блокам с окружением `Env` (имя → `AbstractValue`):

* на входе блока окружения сливаются `join`-ом, поэтому разные ветки дают
  `Unknown`, а совпадающие — конкретное значение;
* `Branch` решается через `evaluate_condition`; решённое условие оставляет ровно
  одну ветвь и **не** добавляет метку к пути (условие доказано, а не угадано);
  нерешённое оставляет обе и добавляет `g<id>=then|else` в путь-свидетель;
* межпроцедурная сводка ограничена: `CallResolver` находит кандидатов по имени,
  аргументы подставляются в параметры формы, глубина ограничена
  (`recursion_depth_limit`), неоднозначность и неразрешённость дают
  `UnresolvedCall`, а не догадку;
* неопределённость пути отслеживается отдельно от свидетеля
  (`uncertain: BTreeSet<BlockId>`), потому что блок можно впервые посетить по
  достоверному пути (тело цикла на первой итерации), а позже — по условному;
* доказательство может только **слабеть**: при повторном посещении
  `Confirmed` понижается до `Possible` и никогда не повышается обратно;
* `Widened` остаётся страховкой на случай недостижения неподвижной точки.

### 5. Причины пробелов — словарь аудита

`GapReason = UnsupportedStatement | UnsupportedExpression |
TernaryInValuePosition | ExceptionDispatch | Widened | UnresolvedCall |
NotInFactContract`.

`NotInFactContract` добавлен в этом инкременте: он отделяет **дыру контракта**
от дыры реализации. `new Foo(...)` не является местом вызова в плоских фактах,
поэтому его нельзя упомянуть в IR — но это известное и равномерное свойство
контракта (`2652` случая на корпусе), а не дефект понижения. Без такого
разделения измерение пробелов показывало бы «2692 неподдержанных конструкции»,
скрывая настоящие 461.

## Последствия

* Появилась модель, на которую можно опереться в N05/N06: `verifyCode` можно
  проверить как значение параметра запроса, а не как совпадение слов.
* Конкурсный ответ не изменился: побайтово тот же `submission.json`
  (`ea3c7ca2…`), S0 = 0.926, 103 шага привязки входа, 0 рёбер без проектного
  места вызова.
* Понижение выполняется на каждом прогоне `tt-export`/`tt-report` для всех
  Java-файлов проекта, то есть корпус из 635 файлов — это ещё и тест на
  устойчивость: 0 паник, 0 структурно некорректных тел.
* Отчёт стал воспроизводимым: порядок свидетелей и обрезок больше не зависит от
  итерации `HashMap` (см. `docs/VERIFICATION.md`, N03/N04).
* Цена: два новых модуля и ~2 000 строк понижения; поддержка ограничена
  матрицей (`docs/SUPPORT_MATRIX.md`), и это ограничение измерено, а не
  заявлено словами.

## Альтернативы и почему они отвергнуты

1. **Символическое исполнение прямо по AST с перебором путей.** Экспоненциально
   на реальном корпусе (циклы + ветвления), и требует AST в ядре — нарушает
   границу стека.
2. **Отдельный анализ на каждый язык (Java — Java, Python — Python).** Дублирует
   решётку, доказательства и отчётность; расхождения между языками стали бы
   расхождениями в качестве анализа. Профиль языка решает только то, что
   действительно различается.
3. **Использовать плоский граф вызовов как CFG (текущий legacy-путь).** Нет
   порядка операторов и условий — именно поэтому `verifyCode` нельзя проверить.
   Путь сохранён как явный `legacy`/кандидатный режим для сравнения.
4. **Считать `Unknown` ложью, чтобы «решать» больше условий.** Нарушает
   `unknown != false` и правило «нет правила `instance.json → solution.json`»:
   такой анализ выдаёт уверенность, которую не может обосновать.
5. **Перенести логику из решений предшественников.** Запрещено условиями задачи и
   не даёт общности: правила были бы привязаны к конкретному проекту.
