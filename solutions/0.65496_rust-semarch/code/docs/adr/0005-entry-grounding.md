# ADR 0005 — Привязка шага сценария к входному обработчику

* Статус: Accepted
* Дата: день 3 (инкремент P1-lite)

## Контекст

Ответ конкурса — подграф исполнения на каждый сценарий. Всё, что попадает в
ответ, достижимо из **входных** обработчиков: сценарий называет действия
пользователя, шаг за шагом, и каждому шагу соответствует один запрос
веб-клиента. Скелет даёт 262 обработчика проекта, но не говорит, какой из них
относится к шагу «Refresh the list of orders filtered by the 'Cancel' status».

Ошибка на входе стоит дважды: неверный обработчик приносит в ответ всё своё
поддерево (падение точности) и теряет верное (падение полноты). Оценка — IoU по
каждому отношению, поэтому вход — самое дорогое решение конвейера.

Текст шага — единственное высказывание о том, что пользователь сделал; он
написан человеком, а обработчик назван разработчиком. Привязка — это перевод
одного словаря в другой по **проектным данным** (маршруты из аннотаций
фреймворка, тексты веб-клиента), без знания сценариев и сущностей.

## Решение

### Три канала, каждый отвечает на свой вопрос

| канал | вопрос | признаки | роль |
|---|---|---|---|
| действие | какой обработчик **делает это**? | маршрут и имя метода; управляющая лексика: объявление, в котором стоит вызов, и элемент, на событие которого он подвешен; лексика страницы | база |
| контракт | какой обработчик принимает **тело такой формы**? | имена полей типа параметра обработчика против payload-части шага | слагаемое с весом `PAYLOAD_WEIGHT` |
| операция | какая это **операция**? | глагол шага против имени метода, маршрута и управляющей лексики | множитель `1 + VERB_WEIGHT × совпадение` |

Все каналы — Okapi BM25 (`semarch_scenario::bm25`) по документам, собранным из
полей с весами: идентичность обработчика один раз, управляющая лексика
`UI_ACTION_WEIGHT` раз, лексика страницы и текстовое окно вокруг вызова — по
одному разу.

### Текст шага читается по ролям, а не целиком

* инструментальные обороты (`from`, `via`, `through`, `using`) вырезаются: они
  называют данные, а не действие;
* предложение делится на клаузы; payload-клаузы (после `with`, `of type`, …)
  идут в канал контракта, а не в канал действия;
* синонимы раскрываются только для глагола действия (первый токен), иначе
  «Open the contact **book**» тянуло бы `preserve`/`create` из существительного
  `book`;
* морфологическое расширение по корпусу ограничено настоящими
  словообразовательными суффиксами (`ment|ance|ence|tion|sion|ness|ity|ure|able|
  ible|age|ist|ism|ant|ent|ary|ory|ive|al|ly|ic|ate`), чтобы `order` не тянул
  `orderid` и `orderservice`.

### Окно вызова — это лексика экрана, а не управления

Текст вокруг запроса в веб-клиенте — в основном подписи полей формы и
идентификаторы payload (`booking_new_contacts_name`, `add_price_first_class_price_rate`).
Это лексика **экрана**, и она входит в документ с тем же весом, что имя файла
страницы. Управляющая лексика — это объявление, внутри которого стоит вызов
(`preserveCreateNewContacts`), и элемент, на событие которого вызов подвешен
(`#ticket_select_contacts_confirm_btn`); только она весит как кнопка.

### Канал операции тонкий и модулирующий

Глагол шага расширяется только для семейств, где **код называет ту же операцию
иначе**: `book` → `preserve`, `reserve`/`buy` → `preserve`, `change`/`update`/
`modify` → `update`/`modify`. Глагол вне таблицы (`open`, `refresh`, `add`)
не расширяется вовсе, и канал для такого шага пуст.

Канал **модулирует** сумму действия и контракта, а не добавляет свой голос:
само по себе совпадение по глаголу слишком дешёвое доказательство (в проекте
десятки `get`/`query`/`list`), но как множитель он упорядочивает именно ту
почти-ничью, которую глагол шага и должен решать.

## Проверенные и отвергнутые варианты

Всё измерено на единственном размеченном сценарии (S0) и на аудите входов
(`examples/entry_audit.rs`, печатает запрос, выбранный вход и ранжированных
кандидатов по каждому шагу; 103 шага в восьми сценариях).

| вариант | измерение | вывод |
|---|---|---|
| канал контракта как **слагаемое** (`PAYLOAD_WEIGHT = 0.6`) | S0 не изменился (0.926: у шагов S0 payload-клауз нет), в скрытых сценариях исправлены шаги бронирования и получения билета (`preserve`, `preserveOther`, `collectTicket`, `executeTicket`), где раньше выигрывали `createNewContacts`, `collectTicket`-соседи и т.п. | принято |
| payload, записанный **без вводного слова** (скобочное перечисление из ≥3 пунктов, притяжательный оборот) как материал канала контракта | S0 не изменился; ни один из 103 шагов не меняет выбранного входа; на «Register a new passenger account (username, password, gender, ID document, e-mail)» верный `UserController#registerUser` поднимается 0.559 → 0.897, но не обходит `createNewContacts` (1.000) — его тянет канал действия, потому что синоним `register` → `create` совпадает с формой «create new contacts» | принято как расширение покрытия канала; остаток разрыва — вопрос канала действия, а не контракта |
| канал операции как **независимый голос** (вес 0.8, полная таблица синонимов) | «Open the details of the first trip found» в четырёх сценариях ушёл с `getTripAllDetailInfo` на короткие `TrainController#query`/`StationController#query`: у общих глаголов (`open` → `get`/`find`/`query`/`list`) выигрывает самый короткий документ | отвергнуто |
| канал операции как **множитель** с полной таблицей | «Book … assurance» исправлен (`addPrice` → `preserve`), но «Add a new route …» и «Add a new high-speed trip …» ушли на `createNewContacts` (расширение `add` → `create`/`new`/`save` попадает в форму «create new contacts»), «Advanced search: the cheapest/quickest …» — на `getByMinStation` | отвергнуто |
| канал операции: **тонкая таблица семейств** + множитель | ровно один шаг из 103 меняется против сборки без канала, и это верный `preserve` вместо `addPrice` | принято |
| окно вызова: вес кнопки (×3) → вес страницы (×1) | 8 из 103 шагов меняются: `addPrice`→`preserve` (с каналом операции), `findByOrderId`→`queryOrdersForRefresh` на «filtered by the 'Cancel' status», `queryAll`×5 → один кандидат на «Open the first new order», `createNewContacts`→`addTrain` на админском шаге; обратная сторона — «Rebook … difference is refunded» ушёл на `payDifference` с разрывом 0.005 | принято с оговоркой (см. ниже) |
| общее хеджирование «почти ничьей» (band `ratio` по всем кандидатам, а не только по семейству) | S0 не меняется (69 рёбер), в скрытых сценариях входов становится больше: S1 541→545, S2 672→679, S4 565→576 | не включено: без эталона скрытых сценариев это ставка на полноту против точности; политика осталась внутри семейства |

## Последствия

* S0 как контроль: **0.926** до и после всего инкремента (executes 0.944 /
  calls 0.885 / remote 1.000 / data 0.875); 96 тестов, clippy без замечаний,
  `submission.json` побайтово воспроизводим, 0 отклонённых рёбер во всех восьми
  сценариях.
* Остаток неверных входов перечислен в отчёте по инкременту; каждый — это шаг,
  для которого веб-клиент не делает отдельного запроса («Open the new order»,
  «Check the price of the order») либо сервис назван иначе, чем в прозе
  (`refund` против `refound`, `consignee` против `updateConsign`). Это
  кандидаты в следующие инкременты, а не повод для правок «под сценарий».
* Порог хеджирования `entry_ratio` остаётся параметром конфигурации
  (`--entry-ratio`, `--max-candidates`), а не константой решения.
