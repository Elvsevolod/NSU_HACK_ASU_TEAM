# ADR 0003 — Разрешение «потенциальных» рёбер скелета в исполняемые

* Статус: Accepted
* Дата: день 1–2 работы над TechArena 2026

## Контекст

Скелет проекта (`skeleton/trainticket.json.gz`) описывает, что код **может**
сделать: у одного места вызова бывает несколько возможных целей, вызов
интерфейса имеет несколько реализаций, а `executes` скелет вообще не размечает.
Ответ конкурса требует другого: что **действительно** произошло в данном
сценарии. Значит, между скелетом и ответом нужен слой вывода, и он обязан быть
объяснимым: за каждое ребро нужно уметь показать основание, иначе ответ
превращается в угадывание.

Требование общности запрещает опираться на имена сущностей, таблиц, сервисов и
сценариев: тот же инструмент должен работать на другом проекте с другим стеком.

## Решение

Ввести набор механизмов разрешения (`crates/semarch-tt/src/graph.rs`), каждый из
которых выводится ровно из одного из трёх источников: (а) семантика языка,
(б) публичный контракт фреймворка, (в) данные проекта. Контракты вынесены в один
data-driven файл (`framework.rs`), так что смена стека — это замена таблицы, а не
переписывание движка.

| # | механизм | источник | код | абляция на S0 |
|---|---|---|---|---|
| G1 | цель объявления/интерфейса заменяется реализацией | семантика ООП + `runtime_dispatch`/`overrides` скелета | `executing_targets`, `overrides` | входит в базу |
| G2 | объявление без тела не исполняется | семантика Java | `drop_declarations` | входит в базу |
| G3 | прокси-репозиторий не метод проекта, но его SQL исполняется | Spring Data: контейнер генерирует реализацию | `is_repository_method`, `attribute_data` | входит в базу |
| G4 | чтение сущности материализует её конструктором без аргументов | JPA: провайдер инстанцирует сущность | `materialized_entities` | база |
| G5 | колбэки уровня запроса исполняются без проектного места вызова | Servlet `Filter`; Spring Security `UserDetailsService`/`UserDetails` | `CallbackSeed`, `framework_callbacks` | база |
| G6 | ветка опциональной возможности, которой нет в сценарии, не исполняется | флаг приходит в запросе; сценарий описывает намерение | `guards.rs`, `call_site_live` | **+0.335** |
| G7 | вызов на получателе-типе разрешается в метод этого типа | разрешение имён Java | `static_receiver_targets` | **+0.036** |

Ключевые правила принадлежности:

* **G3.** Правило конкурса: `data` — это «метод, в котором стоит вызов
  репозитория → таблица». Поэтому SQL прокси приписывается вызывающему методу,
  а сам прокси не попадает ни в `executes`, ни в `calls`.
* **G4.** Тип элемента репозитория разрешается в **один** тип (предпочитается тип
  того же модуля). Сопоставление по простому имени подтягивало одноимённые
  сущности из общего модуля и изобретало рёбра, которых в эталоне нет.
* **G5.** Фильтр `Filter` исполняется, но **не** обходится: обработчик запускает
  Spring, а не метод фильтра, и рёбер `calls` от фильтра к обработчику в эталоне
  нет. `UserDetailsService` обходится, потому что делает настоящую проектную
  работу (SQL). Различие зафиксировано в `CallbackSeed::traverse`.

## Что сознательно **не** делается

* Нет вывода типа получателя для переменных (`qi.isEnableStateQuery()`):
  подстановка типа переменной добавляет рёбра, которых в эталоне нет. G7
  срабатывает только на получателе-типе (`SeatClass.FIRSTCLASS.getCode()`).
* Нет разрешения по «похожести имён» (`queryOrders` ↔ `queryOrdersOther`).
  Одинаковые имена методов в разных сервисах — разные вершины; это прямо
  сказано в справочнике конкурса.
* G6 не считает охраняемой областью всё `if`-выражение. Охраняется только
  `then`-тело: предикат вычисляется до ветвления, ветвь `else` исполняется при
  ложном предикате («флаг не включён» ≠ «флага нет»), а тело `do { … } while (…)`
  исполняется хотя бы раз. Строка, общая для предиката и начала тела, из области
  исключается: по одной строке место вызова нельзя отнести к телу.

## Последствия

* Каждый механизм имеет выключатель (`ResolutionConfig`) и измерен абляцией;
  таблица результатов — в `docs/VERIFICATION.md` и `README.md`.
* Механизмы проверяются на игрушечном проекте (`crates/semarch-tt/tests/generality.rs`),
  который не является Train Ticket: полная замена словаря не меняет результат.
* Ответ можно объяснить: `semarch tt-report` печатает для каждого ребра место
  вызова и связь скелета, а для каждого неисполненного места вызова — признак,
  который его бы оживил (G6). Если одно ребро обосновывают несколько мест
  вызова, отчёт помечает связь `ambiguous` и перечисляет все места вместо
  выбора первого (`mapping: unique | ambiguous | contract`).
