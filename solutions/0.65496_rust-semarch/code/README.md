# semarch

Семантический анализатор графа исполнения: по исходникам проекта и текстам
сценариев он без запуска приложения предсказывает, что **действительно
исполнится** (`executes`), какие вызовы произойдут (`calls`), какие переходы
между сервисами (`remote`) и какой SQL выполнится (`data`).

Задача TechArena допускает чтение исходников, статический анализ и поиск по
тексту, но не допускает запуска проекта и снятия рантайм-трасс. Инструмент — это
чистое статическое рассуждение по данным: скелету проекта, исходникам и текстам
сценариев.

## Что он делает

Скелет описывает **потенциальные** связи (`calls`, `runtime_dispatch`,
`data_access`, `remote_call`). Ответу нужны **исполняемые**. Разрыв закрывают
механизмы, каждый из которых выводится либо из семантики языка, либо из
публичного контракта фреймворка, либо из файлов данных проекта:

| # | механизм | из чего выводится |
|---|---|---|
| G1 | вызов интерфейса → реализация | виртуальная диспетчеризация (`runtime_dispatch`, `overrides`) |
| G2 | объявления без тела не исполняются | семантика Java |
| G3 | прокси-репозиторий исполняет SQL, но не является методом проекта | Spring Data; SQL приписывается вызывающему методу (правило конкурса) |
| G4 | чтение сущности материализует её | JPA: провайдер вызывает конструктор сущности без аргументов |
| G5 | колбэки уровня запроса | Servlet `Filter`, Spring Security `UserDetailsService` / `UserDetails` |
| G6 | опциональные ветки, которых нет в сценарии, не исполняются | флаг приходит в запросе; сценарий описывает намерение |
| G7 | вызов на получателе-типе → метод этого типа | разрешение имён Java (`SeatClass.FIRSTCLASS.getCode()`) |

Дополнительно входной обработчик сопоставляется шагам сценария. Признаки шага
разделены по роли, и каждый канал отвечает на свой вопрос:

| канал | вопрос | признаки |
|---|---|---|
| действие | какой обработчик **делает это**? | маршрут и имя метода + управляющая лексика: объявление, внутри которого стоит вызов, и элемент, на событие которого он подвешен, + лексика страницы |
| контракт | какой обработчик принимает **тело такой формы**? | имена полей типа параметра обработчика против той части шага, что описывает payload |
| операция | какая это **операция**? | глагол шага против имени метода, маршрута и управляющей лексики |

Текстовое окно вокруг вызова — это не управляющая лексика, а поле формы и
идентификаторы payload (`booking_new_contacts_name`); оно входит в признаки
действия с тем же весом, что и имя страницы, а не трижды, как кнопка.

Контракт отвечает на шаг-команду («Book … with food and assurance» описывает
поля `foodType`/`assurance` тела `OrderTicketsInfo`); у шага-чтения payload нет,
и канал в ранжировании не участвует вовсе, поэтому ответы на чтение не
меняются от его появления. Field-список, записанный без вводного слова — скобочное
перечисление («Register a new passenger account (username, password, gender,
ID document, e-mail)») или притяжательный оборот («the consignee's name and phone
number») — тоже считается payload: это перечень полей тела запроса, а не объект
действия.

Канал операции *модулирует* сумму действия и контракта, а не добавляет свой
голос: глагол шага расширяется только там, где код называет ту же операцию
иначе (`book` → `preserve`, `change` → `update`/`modify`), а шаг вроде «Open …»
не называет никакой операции проекта и канал для него пуст. Так различаются
«Book … first-class seat … assurance» → `preserve` и «Add a price configuration
… first class rate 1.2» → `addPrice`, у которых совпадают существительные.

На выходе действует политика «почти ничьей»: у семейства одноимённых обработчиков
удерживаются все кандидаты, чей балл не ниже `ratio × лучший` — сценарий
оценивается целиком, поэтому осторожное хеджирование на входе не теряет цепочку,
а различающая лексика семейства (тип поезда из предыдущих шагов) выбирает
вариант.

Ни одно правило не знает Train Ticket, имена сущностей, таблиц или сценариев.
Это проверяется тестом ренейм-независимости (см. ниже).

## Сборка и запуск

```sh
cd semarch
cargo build --release -p semarch-cli

# ответ: ./submission.json
./target/release/semarch tt-export  <challenge-root> --out submission.json

# аудит: почему каждое ребро есть
./target/release/semarch tt-report  <challenge-root> --out report.json

# тень: ответ не меняется, рядом пишется дифф движка значений
./target/release/semarch tt-export  <challenge-root> --out submission.json \
    --mode shadow                                     # → submission.shadow.json

# семантический аудит: привязки, решения, сертификаты отсечений, счётчики
./target/release/semarch tt-semantic <challenge-root> --out audit.json

# проверка: 224 теста в 40 наборах, включая тест общности
cargo test
```

`<challenge-root>` — каталог с `skeleton/`, `scenarios/`, `targets/`
(в этом репозитории это `tt-challenge/`). Для сданного архива набор входов
достаточно распаковать рядом: инструмент не меняет их и не требует сети.

Полезные ключи:

```sh
semarch tt-export <root> --explain                     # ранжирование входов по шагам
semarch tt-export <root> --scenarios S0                # один сценарий
semarch tt-report <root> --scenarios S0                # аудит одного сценария
semarch tt-export <root> --disable guards,static       # абляция механизмов
semarch tt-export <root> --entry-ratio 0.95 --max-candidates 4
semarch tt-export <root> --mode semantic               # ответ движка значений (N06)
semarch tt-export <root> --mode shadow --shadow-out d.json
```

`--mode legacy` (по умолчанию) — сдаваемый ответ: привязка входов и обход
графа вызовов. `--mode shadow` оставляет ответ **тем же** и пишет отдельный
дифф против движка состояний сценария (у каждого ребра — объяснение).
`--mode semantic` отдаёт ответ движка: значения полей запроса, решения охран и
межпроцедурная передача объектов (ADR 0007).

На восьми сценариях конкурса `--mode semantic` теперь совпадает с legacy
**побайтово** (в S0 — 69 рёбер; до инкремента B38 движок добавлял к ним пять
ложных рёбер, порождённых gap-блоками, и получал 0.618 против 0.926). Совпадение
— измеренный результат, а не цель: движок ничего не теряет из legacy и ничего не
добавляет к нему. Ценность семантического пути — не другая оценка, а
провенанс: у каждого отброшенного места вызова есть сертификат (охрана, строка,
вердикт, свидетельский путь, блоки; ADR 0008), у каждой привязки — источник
значения, у каждого пробела — причина. Это видно в `tt-semantic`.

Полный экспорт восьми сценариев занимает ~0,15 с.

## Как это проверялось

Открыт эталон только по S0 (`gold/S0.json`): 34 `executes`, 24 `calls`,
0 `remote`, 7 `data`. Всё измерено на нём, ничего не предполагается:

| конфигурация | балл S0 | executes | calls | remote | data |
|---|---|---|---|---|---|
| все механизмы (**ответ**) | **0.926** | 0.944 | 0.885 | 1.000 | 0.875 |
| `--disable guards` | 0.591 | 0.791 | 0.697 | 0.000 | 0.875 |
| `--disable static` | 0.855 | 0.842 | 0.704 | 1.000 | 0.875 |
| `--disable guards,static` | 0.558 | 0.744 | 0.613 | 0.000 | 0.875 |

Каждое лишнее ребро и каждое отсутствующее разобрано поимённо в
[`docs/VERIFICATION.md`](docs/VERIFICATION.md): остаток — это причуды разметки
(например, `getToken → User#getPassword()`, которого в исходнике нет), а не
ошибки механизмов.

## Общность

`cargo test -p semarch-tt --test generality` строит игрушечный проект дважды:
во второй копии переименовано **всё** — модуль, типы, методы, сущность, таблица,
фильтр, принципал, id сценария и текст шага. Предсказанная структура обязана
совпасть, и это проверяется на реальном конвейере (скелет + исходники +
интерфейс + сценарий + экспортёр): если бы какое-то правило опиралось на имя,
два прогона разошлись бы. Тест не использует Train Ticket.

## Роль модели (ML) и LLM

Модель не находится в контуре принятия решения и не нужна для воспроизведения
ответа. Интерфейс ранжирования устроен так, что обучаемая переоценка может быть
включена позже, но включается она по измеренному критерию, а не по вкусу; файл
модели при этом допустимо держать прямо в репозитории (каталог `models/`).
Подробно — [`docs/adr/0004-ml-and-llm-boundary.md`](docs/adr/0004-ml-and-llm-boundary.md).

LLM человек использует **рядом** с инструментом: `report.json` перечисляет для
каждого ребра место вызова (`файл:строка`, получатель), тип связи скелета, а для
каждого неисполненного места вызова — признак, который его бы оживил. По этому
файлу путь можно проверить руками или скормить модели на ревью, не доверяя
движку. Никакая гипотеза модели не попадает в ответ, пока не выражена как
механизм и не подтверждена абляцией.

## Провенанс идей

Заимствованы только алгоритмы и научные идеи, код написан свой:

* **Okapi BM25** (Robertson & Walker, 1994) — ранжирование входных обработчиков;
* **summary-based interprocedural propagation** (классический data-flow) —
  распространение исполнения по графу с ограничением глубины;
* **name-based call graph + may-closure** (как в инструментах вида Soot/WALA) —
  построение достижимости;
* **two-stage retrieval** (лексический ранкер + опциональная переранжировка) —
  рамка из линии работ TOSS.

Грамматики зафиксированы в [`docs/adr/0002-grammar-pin.md`](docs/adr/0002-grammar-pin.md).
