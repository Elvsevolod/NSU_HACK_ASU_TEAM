# E17–E21: выбор чтения по доказанной истории

Рабочая база — проверенный E16. Source-backed lexical поиск иногда отказывался между чтением одной записи и списком, хотя сценарий прямо ссылался на только что созданный объект. Новый ограниченный resolver проверяет существующие кандидаты и факты исходников, не меняет scores и frozen margin 8%.

Разрешается только прямой GET с единственным обязательным PathVariable, единственным типом результата и явной ссылкой на предыдущее создание. Native kind параметра подтверждается namespace-aware правилами Java и типом исходного поля. POST producer и выбранный response producer должны завершиться полностью, вернуть совместимый тип и согласованный ID; оба observation digest записываются. Коллекция, два подходящих endpoint, неподтверждённый тип, более позднее неполное создание, несколько упомянутых сущностей или UI-guard не превращаются в один выбранный запрос. Поддержанные ID здесь — native String и integral kinds; полного NL planner нет.

E17 разрешил первое чтение. E18 добавил связь более свежего response с исходным созданием и отказ при утраченном source producer. E19 проверял selected-object ссылку через поле ответа. E20 упростил это: для данного правила берётся сам response field, а не параметры обновления и не selected bookkeeping. Поэтому String-ответ update не подменяет предыдущий ответ с записью. Если observation digest остаётся неизвестным, разрешение не выдаётся. E21 устраняет два новых контрпримера: многосоставное действие не сводится к чтению одной сущности; JSON-тело у GET без RequestBody даёт диагностику, включая случай первоначального lexical отказа.

31 новый source fixture находится в `code/tests/test_history_request_choice33.py`. Полные исторические before/after, включая исправленные ошибочные предположения в тестовых спецификациях, сохранены в `development/history-review-e21/review.json` и stage patches. Frozen oracle реальных проектов не менялся. Первые контролируемые before-сбои: E17 — 3, E18 — 1, E21 — 2; промежуточные дополнительные контрпримеры и неудачные проверки тоже сохранены.

Это новое development-правило поверх прежнего отказа B, а не новая калибровка его ranking. Исторические frozen A/B и ML результаты не переименованы. Source history constraint применяется отдельно от модельных scores, не передаёт модели значения или право создавать рёбра и не обходится в explicit HTTP mode.

Новый парный model experiment выполнен на одном E20: `development/semantic-model-review-e20/review.json`. При обязательном строгом wire/origin контроле полноценные NL цепочки не проходят. Same-candidates и expanded не дали разницы в итоговых ответах. Границы: английский prior-creation шаблон; compound scheduling, свободный русский NL, полный TT UI, некоторые типы и ORM queries, отсутствующий server route и exact error bytes остаются неподдержанными.
