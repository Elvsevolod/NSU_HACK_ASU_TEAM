E22 разрешает прежний lexical отказ только при единственном singular GET, явном имени исходной сущности и конкретном параметре пути. Проверяются source type поля и native kind, диапазон числа, отсутствие конкурирующего endpoint, UI и составного запроса. Ранжирование и8% margin не менялись. Before:6failed/11passed. E23 распознаёт `Repeat` с указанным глаголом и его ing-формой. Это изменение определения операции поиска; буквальный JSON, значения параметров, состояние и число запросов не выводятся из слова Repeat. Before15failed/5passed;20 новых проверок проходят. При проверке обязательного R06 обнаружен отдельный дефект обычного grounder: HTTP500 с body Parcel{id:7} давал успешно привязанный новый id7. Это не был только lexical tie. Независимое воспроизведение — `benchmark/r06-failed-response-probe`; новый12-case набор before6failed/6passed. E24 запрещает брать response-derived значения из failed или incompletely explored engine observations: ID, related selection, body prefill и role fields. Неудачная более поздняя попытка создания не заменяется старой успешной. Известные клиентские input parameters не стираются; более ранний успешный response остаётся допустимым producer после неудачного чтения. В двух прежних E18 тестах ожидание уточнено: проверяется точный digest/ссылка на исходный успешный producer, а не запрет пользоваться уже известным ID после failed GET.

Граница compatibility: голые legacy history rows без outcome/exploration трактуются как явно предоставленные наблюдения; они не получают выдуманных complete metadata. Нормальные engine histories всегда содержат outcome и exploration; эти поля обязательны для оценки их доступности. Group agreement остаётся строгим во всех завершённых исходах. Новые допущения об успешности error body не вводятся, состояние базы и уже выполненные effects не удаляются.
