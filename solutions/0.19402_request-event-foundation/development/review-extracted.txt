Что из этой истории можно заключить
Перенос ответов и состояния действительно важен. Рост № 2→3→4 на сайте — существенное сохранённое свидетельство. Но изменения смешаны, поэтому отдельно приписать прирост HTTP, ORM или идентичности нельзя.
Компонентное исправление может быть полезным и не менять основной ответ. Побайтно совпадают № 7/8, № 12/14, № 15/16 и № 18/19/20/22/23. Это особенно важно для оценки поздней разработки: больше тестов и поддержанных конструкций не означают автоматически лучший сценарный прогноз.
Причины скрытого падения не доказаны. У № 15, например, существенно меняются S1–S7, а S0 остаётся тем же. Без скрытых эталонов нельзя установить, какие новые рёбра правильны, и распределить потерю качества № 12→18 между отдельными изменениями.

3 Основные подтверждённые ограничения
Далее Vn означает снимок № n из каталога. У основной ветки модули находятся в code/analyzer/, у № 13 — в code/polygraph/. Полные пути и глубина чтения приведены в отчёте.
3 1 Источник значения проверяется слабее чем его смысл
Наблюдаемый факт № 6: сохранённый replay S0 сначала получает userId, затем передаёт в accountId имя пользователя. Provenance отмечен как разрешённый context:username. Другая коррекция модели заменяет запрос заказов запросом станций.
Значение существует и подходит по типу String, но не является нужным идентификатором. Поэтому уменьшение unknown и schema-valid JSON не доказывают правильного связывания.
В позднем V20/contracts.py, ContractGrounder.step, строка 306, шесть лучших кандидатов сохраняются для диагностики; исполняется первая удовлетворимая группа. Это не полноценное исследование шести возможных обработчиков. Кроме того, удаление префикса As … в ранжировании способно потерять значимую роль пользователя.
Проверка: одинаковое действие для student и librarian, которым соответствуют разные доступные endpoints. Actor должен стать ограничением выбора; при недостаточных данных нужна явная неоднозначность.
3 2 Начальный и межсервисный запросы проходят разные границы
V20/__main__.py, строка 94, передаёт выбранные entry и уже преобразованные params непосредственно в path runner. Строгий http_binding работает преимущественно на реконструированных downstream HTTP-запросах. Этот предел прямо отражён в DIAGNOSTICS.md.
Следствие: улучшение query/path/header binding в № 20 ещё не исправляет всю цепочку пользовательского входа.
Проверка: один endpoint и одинаковые данные подать как explicit HTTP, через исходный UI и через однозначный NL-шаг. Выбранный маршрут, параметры, отказ до handler и граф должны совпасть.
3 3 История теряет принадлежность результата конкретной коллекции
В V20/provenance.py, history_value, строка 259, коллекциями считаются только группы с len(keys)>1. Тот же механизм сохранён в № 26.
Статически выведенный контрпример: список [A,B], затем новый список [C], затем «открыть первый». Свежий singleton исключается из выбора, и берётся старый A. Пустой новый список также должен запрещать возврат к старому результату.
Это ошибка представления истории: после разворачивания объектов теряются shape контейнера и producer. Дополнительный риск — identity на строке 209 не включает deployment/FQN; два сервисных типа Invoice с одинаковым ID могут смешаться.
Нужны отдельные ObjectRef и CollectionRef: сервис, квалифицированный тип, идентификатор, породивший запрос, порядок, полнота ответа и выбранный объект.
3 4 Неизвестный вызов и неопределённое значение смешаны
В V26/engine.py, строка 2605, финальный fallback неизвестного вызова инвалидирует отдельные JavaList/mapper, но не задаёт общий контракт изменения DTO, переданного Map, ресурсов и возможного исключения. Имена debug/info/print обходят даже эту обработку без доказанного класса.
Контрпример:
dto.active = false;external.mutate(dto);if (dto.active) reserve();
Без модели external нельзя сохранять active=false как установленный факт. Но глобальный сброс всех таблиц, испытанный в № 21, слишком разрушителен.
Нужна модель результата, доступной для изменения памяти, ресурсов, callbacks и normal/throw. Граница эффекта должна опираться на сигнатуру, source/config и доступные зависимости; её нельзя произвольно ограничить только аргументами, если вызов имеет доступ к globals или сервисам.
3 5 Альтернативы способны образовать состояние которого нет ни в одном пути
№ 22 исправляет внешний replay, совместно копируя state и params. Однако в V26/engine.py, строки 2173 и 2240, при исчерпании выбора несколько local/remote targets перебираются на общем состоянии.
Предлагаемая проверка: взаимоисключающие стратегии делают count++ и count--, затем выполняются проверка count==0, обязательная запись и следующий GET. Последовательное применение обеих стратегий создаёт ложный ноль. Также необходимо проверить время жизни счётчика uncertain, который в этих ветках остаётся повышенным.
Для каждой альтернативы нужен совместный fork receiver, args, heap и state, затем корректное объединение.
3 6 Даже некоторые простые модели Java и API дают конкретно неверный результат
По чтению № 26:
engine.execute, строка 1070: do обрабатывается вместе с циклом, проверяющим условие до тела; return из do…while(false) может потеряться.
engine.py, строка 2539: isBlank моделируется как пустота; пробельная строка обрабатывается неверно.
models.library, строка 409: Java split заменён Python literal split. Например, "a,".split(",").length в Java должно дать 1.
_invoke, строка 530: ключ активного вызова не содержит receiver; два разных узла next.step() могут ошибочно выглядеть как рекурсия.
Первые три расхождения проверены против JLS §14.13 и String API. Новые тесты не запускались. [1, 2]
Рост числа тестов до 1 464 не закрывает эти пробелы. Нужны независимые проверки порядка вычисления, исключений и точных библиотечных контрактов.
3 7 data ещё часто означает потенциальную проводку ORM
V26/engine.py, repository, строка 2986, добавляет data для ресурсов wiring до определения фактической операции. Нет полноценного persistence context, dirty checking, lazy/flush/rollback. getReference/getById обрабатываются близко к eager read.
Проверки должны различать reference→ID и reference→поле, повторное чтение, managed mutation→commit, save→throw и flush→throw. SQL, который выполнился и затем откатился, остаётся событием data; committed-состояние при этом откатывается. Deferred save без flush не означает, что SQL уже был.
Документация Spring Data отдельно указывает provider-dependent поведение reference и отложенного исключения. Она подтверждает необходимость такой границы, но не заменяет модель версии Train Ticket. [3]
Проекция callbacks также неодинакова: JSON № 26 различает отражённый root constructor и вложенные source-вызовы, а ORM materialization на строке 3144 может экспортировать конструктор обычным способом.
3 8 Возможные рёбра экспортируются как основной прогноз
В V23/__main__.py, строки 120 и 160, итог строится как union. confirmed/possible остаются диагностикой. Первое общее предположение способно сделать условными все следующие рёбра; у № 20/22/23 сохранено 0 confirmed и 4 413 possible.
При fallback V26/engine.py, строка 602, добавляет целое потенциальное замыкание метода. Неподдержанная операция перед заведомо ложной веткой с remote может вернуть этот remote в ответ.
Нужна причинность отдельного события: request, callsite, guard, использованные значения и предположения. Простое переключение на must-only тоже опасно — оно может резко обрушить полноту. При неоднозначном входе следует сохранять условные варианты; политику единственного экспортируемого графа проверять отдельно.

5 Внешние инструменты
Исследование из пакета прочитано полностью. 90 карточек — каталог, 43 источника — исследовательская база, 18 design-cases — спецификации будущих проверок. Они не являются прогоном 90 движков или 18 пройденными тестами.
Свежая проверка выполнена 18.10.2026 по первичным источникам. Общего benchmark памяти/времени кандидатов на вашем входе нет; ниже приведена цена зависимости и интеграции.

Что добавил поиск вне простого повторения каталога
Jasmine адресно моделирует Spring DI/AOP поверх Soot/Doop. Стоит заимствовать правила регистрации и независимые примеры. Его Java8/Docker pipeline и конфигурация экспериментов не подходят как автоматически лёгкая зависимость; указанные авторами 128 GB не являются нашим измерением или минимальным требованием. [23]
RESTler полезен идеей producer→consumer: значение ответа становится аргументом следующего запроса. Сам инструмент использует OpenAPI и живое исполнение API, поэтому в эту задачу целиком не подходит. Нашему grounder нужна статически восстановленная версия такой зависимости. [24]
CSE for the Next 700 Memory Models, OOPSLA 2025 поддерживает направление summaries с предусловиями на читаемую часть памяти. Gillian Debugging, 2026 даёт полезную идею структурированных событий и восстановления дерева исходного исполнения. Для проекта нужен этот диагностический протокол; пользовательский интерфейс сейчас не требуется. [20, 25]
6 Рекомендуемая архитектура и стоимость объединения

Факты отделяются от выбора. Skeleton задаёт ID и кандидатов; source/config уточняют декларации, endpoints, DTO, entities, profiles и beans. В фактах нет правил Train Ticket action→route.
Вход execution — единый запрос. Он содержит deployment, verb, URL/path/query/header/body, content type, actor/session и provenance каждого значения. Отсутствие, null, известное, символическое и неизвестное значение различаются. Начальный и remote запросы используют одинаковый binder.
Состояние принадлежит пути. Snapshot сохраняет aliases внутри альтернативы и изолирует её от остальных. HTTP/JSON создаёт wire copy. История хранит producer и контейнер ответа. Request failure и следующий пользовательский шаг — разные уровни управления; это также исправляет преждевременную остановку всего сценария в V13/polygraph/analysis.py, строка 38.
Модель библиотеки возвращает эффекты и завершение. Требуются value, reads/writes, callbacks и throw conditions с версионированной областью применимости. Общие Java/Spring/HTTP-правила допустимы; ручная бизнес-логика приложения — нет.
Граф строится из событий. Причина вызова отличает direct call, framework dispatch, reflection root и вложенный callback. SQL events отделены от committed DB. Для каждого ребра сохраняются условия и граница знания.
Summaries и SMT вводятся после этого. Summary требует source/model/config versions, receiver/alias и read-state preconditions; одного метода с args мало. У № 13 на TT сохранено ноль solver checks, поэтому само присутствие Z3 ещё не приносит пользы.

Для заявления переносимости нужны существующие независимые приложения, а не только переименования Train Ticket и короткие строки Java. Предложение для согласования — как минимум две внешние предметные области плюс отложенные сценарии, при этом маленькие контрпримеры остаются отдельным уровнем проверки.
Spring Petclinic Microservices подходит как кандидат для закреплённого HTTP-подмножества Customers/Visits/Vets; это другой уровень проверки, чем body probes в пакете. Текущий проект включает дополнительные подсистемы, поэтому профиль надо зафиксировать явно. PiggyMetrics уже использовался в разработке и новым blind holdout не является. [26]
В каждом сценарии следует отдельно оценивать выбор endpoint, каналы и значения аргументов, status/result, изменения состояния, затем precision/recall/IoU четырёх отношений. Обязательно показывать число случаев с непустыми gold remote/data. Правильные запросы допустимы в диагностическом контроле execution-layer; продуктовый grounder не должен получать их из oracle.
8 Ограничения этого заключения
Полностью не восстановлены исторические трассы всех 103 шагов: benchmark/analysis-report.json отсутствует во многих папках, а часть поздних experiments/20261018-* не включена. Сводки позволяют проверить результаты, но не причину каждого ребра и unknown.
Не прочитаны построчно все повторяющиеся версии каждого модуля, все тысячи тестов и весь Train Ticket. Исследованы существенные изменения и конкретные семантические участки; SQL — по структуре, типам и выбранным значениям. Точная карта глубины чтения находится в отчёте.
Дублирующие ZIP остальных решений отсутствуют согласно комплектации; их прежнее сравнение записано в package_checks/original_archives.json. Для № 13 оригинал проверен отдельно, текущая воспроизводимость не заявляется. Скрытых gold S1–S7 нет, сайт повторно не посещался. Внешние движки не запускались и не измерялись в общем окружении.
Следующий законченный результат разработки должен быть таким: независимая многошаговая Java/Spring-цепочка проходит единый source-derived запрос, корректно меняет изолированное состояние и выдаёт граф с проверяемым основанием каждого ребра. Именно этот результат даст основание выбирать дальнейшие Java-модели, внешний extractor, summaries или локальную модель.
