## Что изменено

- Один неизменяемый `Request` и общий binder для explicit HTTP, исходного UI, NL и межсервисного запроса; различаются missing/null/unknown, каналы и происхождение значений, учитывается actor.
- История хранит producer, контейнер, deployment/FQN, порядок и тип объектов; свежие пустые/одиночные ответы не подменяются старыми объектами.
- Альтернативы совместно копируют receiver, аргументы, heap, БД и историю, сохраняя aliases внутри пути. Normal/throw продолжаются отдельно; исчерпание бюджета явно останавливает неподдержанное продолжение.
- Исправлены do/while, continue/throw/finally, Java isBlank, ограниченный regex split, ключ вызова с receiver и порядок инициализаторов.
- Неизвестные вызовы описывают затронутую память, callbacks и возможный отказ. Имя `info` само по себе не доказывает Logger. Несвязанные таблицы без основания не сбрасываются.
- Экспорт опирается на события с request, callsite, guard, значениями и предположениями. Статическое замыкание остаётся отдельным списком кандидатов.
- JSON и ORM используют согласованную проекцию отражённых корневых вызовов, сохраняя вложенные source-эффекты. Поддержаны ограниченные REQUIRED transactions, flush/rollback, managed identity/dirty checking, lazy references/collections.
- TableStore использует COW; summaries исходных getter-эффектов проверяют версии, receiver и aliases. Возвращаемые значения по одному имени метода не кешируются.

## Независимая проверка

Полная синтетическая цепочка из 11 NL/HTTP-шагов gateway → warehouse точно воспроизводит 18 рёбер всех четырёх отношений, результаты и состояние. На закреплённых исходниках Petclinic Customers (7 шагов) и PiggyMetrics account read/duplicate (3 шага) совпали endpoint, проверяемые поля аргументов и результатов, status, состояние и граф. Некоторые payload в oracle помечены `ignore_result`, они не измерены. Эталоны доступны только проверяющей программе.

Это ограниченные профили: реальный remote в двух публичных цепочках пуст; он проверен в синтетической цепочке. PiggyMetrics уже использовался в разработке, успешная цепочка создания с Feign/statistics не проверена. Первый прогон отложенных сценариев обнаружил ошибку explicit JSON; после исправления оба случая прошли как регрессионный повтор. Чистый blind holdout не заявляется.

JavaParser, Z3 и локальный Qwen испытаны отдельно. Основания делать их обязательными зависимостями не получено. Результаты и затраты сохранены в `benchmark/optional-*`.

## Воспроизведение

Из каталога решения с Python 3.11. Зависимости основного анализатора закреплены в `requirements.txt`:

```sh
python -m pip install -r requirements.txt
PYTHONPATH=code python -B -m pytest code/tests -q -p no:cacheprovider
python -B code/offline_run.py --source ../../tt-challenge/targets/trainticket --skeleton ../../tt-challenge/skeleton/trainticket.json.gz --context ../../tt-challenge/context --scenarios ../../tt-challenge/scenarios --output /tmp/analyzer27-submission.json --report /tmp/analyzer27-report.json
python -B code/verify_run.py --help
```

В распакованном архиве передайте собственные абсолютные пути входов вместо `../../tt-challenge/...`. Продукт принимает готовый skeleton; построение skeleton для контрольных публичных профилей находится только в проверяющем адаптере. Повтор анализа с готовым индексом воспроизводит `checks/repeat_prepared.py`.

Офлайн-запуск запрещает обращения к сети, дочерние процессы и чтение эталонов/прежних ответов. В `benchmark/final/analysis-report.json.gz` сохранена полная диагностика финального прогона, в `witness-check.json` — проверка оснований. Политика экспорта по умолчанию `observed-union`; режим `confirmed` сравнивался отдельно и потерял ожидаемые рёбра на трёх контрольных цепочках.

Архив создаёт `checks/package_final.py`; унаследованный `code/package_solution.py` относится к старой структуре бенчмарка и в этом варианте не используется. После отправки `solution.zip`, код и ответ не пересобираются. Оценка и подтверждение сайта записываются отдельно.
