# Почему № 27 провалился и что делать дальше

Инженерный разбор от 18 октября 2026 года. Основание — присланный пакет solution_27_after_review_2026-10-18.zip, предыдущие снимки и сохранённые измерения. Все выводы и приложения собраны в этом документе.

## 1. Основной вывод и выбранное направление

**№ 27 сделал частичную модель исполнения строже, но её пробелы стали останавливать полезное вычисление. Неполное распознавание типов и библиотечных операций превращается в возможные исключения и потерю состояния; бюджет альтернатив заканчивается; продолжение запроса исчезает из графа. Это главный подтверждённый механизм потери ответа.** Одновременно сохранились ошибки связывания сценария с запросом, а новый Request иногда теряет уже выбранные параметры. [F03](#f03) [F04](#f04) [F05](#f05) [F06](#f06) [F11](#f11)

**Мой предыдущий разбор недостаточно жёстко ограничил объём следующей итерации.** Полезные архитектурные идеи превратились в пакет из 18 пунктов, который можно закрывать ограниченными проверками, продолжая ухудшать конечный сценарный прогноз. Нужно было поставить обязательное условие: сначала один полный путь с известными запросами, значениями и рёбрами, затем следующее изменение. Особенно опасное сочетание — новые opaque effects, completion replay и исключение статического замыкания из ответа — следовало проверять отдельно до переноса остальных механизмов. [F01](#f01) [F15](#f15) [F18](#f18)

Выбираю **узкий ремонт причинной цепи на отдельной копии № 27**, с неизменённым № 23 как контролем и № 5 как сохранённым специализированным ориентиром. В следующем варианте сначала должны исчезнуть конкретные необоснованные остановки на Logger/String, исправиться перенос выбранной альтернативы и сохранение уже достигнутого remote. Затем — восстановление аутентификационного receiver и фактического Request. Каждое изменение проверяется отдельно. Замену ядра, новые языки, обязательную локальную модель и дальнейшее расширение ORM сейчас откладываем.

Это выбор направления исследования, а не утверждение, что несколько исправлений вернут 0,66 или дадут 0,91. Скрытых эталонов S1–S7 нет, однофакторных повторных прогонов после моих исправлений нет, сами исправления в этой проверке не выполнялись. Установлены конкретные дефекты и наблюдаемые последствия; их доли в скрытом score ещё не измерены.

## 3. Главная поломка: потерянный тип превращается в остановку запроса

### 3.1. Обычный Logger не узнаётся в квалифицированной записи

В исследуемом исходнике поле явно имеет тип SLF4J Logger:

```java
private static final Logger LOGGER = LoggerFactory.getLogger(...);
TravelServiceImpl.LOGGER.info(..., trips);
// далее формируется HttpEntity и вызывается RestTemplate.exchange(...)
```

В № 27 Project.extract_metadata сохраняет статические поля отдельно в static_field_types. Engine.source_type читает этот индекс для простого идентификатора LOGGER, но ветка ClassName.LOGGER проверяет другие индексы и статический тип не получает. Новый обработчик logging требует доказанный тип Logger; при пустом declared_receiver он отправляет info/debug в общий apply_unknown. [F05](#f05)

Это подтверждено конкретной трассой, а не только предполагаемым контрпримером. В S1, шаг 2, запрос поиска уже имеет осмысленный endpoint и параметры Shanghai → Suzhou. Одна из альтернатив доходит до TravelServiceImpl.getTicketsByBatch и останавливается на LOGGER.info на строке 343. RestTemplate.exchange находится на строке 347, но этот путь до него не доходит. В S1, шаг 3, все восемь альтернатив либо останавливаются на LOGGER.debug перед repository query, либо заканчиваются opaque-исключением на logging. [F04](#f04) [F05](#f05)

В финальном report — 1 090 записей opaque info, 96 warn, 24 debug и 31 error. Для перечисленных logging-записей тип receiver пуст. Числа повторяют общие префиксы; например info соответствует 52 различным callsite, а не 1 090 независимым местам программы.

У № 23 и № 26 logging пропускался по имени метода. Это чрезмерно широкая эвристика, которая могла скрыть пользовательский метод info с настоящими эффектами. Замена её проверкой типа разумна. **Ошибка внедрения — потребовать тип, не обеспечив его разрешение для обычной формы Java.** Возвращать безусловное игнорирование всех info нельзя; нужно исправить общий доступ к статическим полям, imports, квалификаторам и затенению имён. Известная модель SLF4J должна применяться к обеим эквивалентным формам. При ремонте нужно сохранить вычисление аргументов, а вызовы пользовательского кода при форматировании моделировать в пределах явно заданного контракта Logger. Текущий no-op по типу сам по себе этого не обеспечивает. Обещание «любой logging никогда не бросает и ничего не вызывает» было бы слишком сильным. [F05](#f05) [W02](#w02)

### 3.2. Модель умеет вычислить строку, но теряет тип собственного результата

В StringUtils.String2Lower исходный код возвращает:

```java
return str.replace(" ", "").toLowerCase(Locale.ROOT);
```

Модель в models.py умеет вычислять replace и toLowerCase для конкретной строки. Однако source_type не описывает возврат replace, а toLowerCase узнаёт как String только без аргументов. Для overload с Locale метаданные результата не согласованы с вычисленным значением. Последующий строгий reference conversion превращает уже полученную строку в U. Затем length на неизвестном значении попадает в opaque effects. [F07](#f07)

В S1, шаг 2, сохранена диагностика unresolved implicit reference cast именно для этой цепочки и последующий opaque length в TravelController. Следовательно, отсутствие списка поездов нельзя объяснить только плохим NL: в этом примере endpoint и исходные поля уже выбраны по делу, а результат теряется внутри исполнения.

Здесь важно происхождение дефекта. Пробел source_type существовал в № 23. В № 26 строгий return conversion уже отбрасывал такое значение; по этому сопоставлению нельзя установить, в каком именно донорном изменении оно впервые стало теряться. № 27 добавил к последствиям opaque-исключение, изменения памяти и остановку по бюджету. Это взаимодействие унаследованного и нового поведения. [F07](#f07)

Правильный ремонт — согласовать распознанную сигнатуру, абстрактное значение, доказанный тип результата, эффекты и допустимые завершения в одном контракте модели. Для доказанного String с неизвестным содержимым length остаётся известной операцией с целочисленным результатом; неизвестное значение строки не делает семантику length произвольной. Для locale и Unicode требуется явно ограниченный поддерживаемый профиль: замена Java semantics вызовом Python lower без оговорок недостаточна. API Java подтверждает, что overload toLowerCase(Locale) возвращает String. [W01](#w01)

### 3.3. Загруженный User не передаётся в callbacks аутентификации

Engine.authentication вызывает loadUserByUsername и игнорирует возвращённый объект. Затем getPassword, getAuthorities и другие UserDetails callbacks вызываются без receiver. _invoke создаёт пустой this, поэтому чтение roles не использует загруженного пользователя. Дополнительно не закрыт constructor method reference в цепочке stream/map/collect. Сам authenticate после callback-модели может дойти до общего opaque handler. [F08](#f08)

В S1 на шаге входа семь из восьми альтернатив теряют точность auth_user/user_roles; единственный returned не даёт успешного входа. У этого login нет успешного ответа, из которого можно перенести token и идентификаторы в последующие шаги. Новый журнал истории добросовестно записывает неизвестный результат, но восстановить значение из него не может. Это старый дефект callback receiver, усиленный новой политикой исполнения. Ремонт требует передать тот же объект principal через все поддержанные callbacks; нельзя подставить фиктивный успешный login или константу токена. [F04](#f04) [F08](#f08)

### 3.4. Бюджет превращает эти локальные пробелы в каскад

CallEffects по умолчанию содержит normal и throw. apply_unknown требует изолированное продолжение, а paths.run_paths расходует общий completion_budget=max(8, limit). В финальном прогоне limit=4, бюджет завершений равен 8. При его исчерпании Engine.run ловит AnalysisBoundary, возвращает U и прекращает текущий запрос. Будущие связи остаются только в static_candidates. [F06](#f06)

У apply_unknown есть и дополнительная потеря точности: reachable roots включают receiver, аргументы и this вызывающего метода; source_resources использует потенциальные data-зависимости без полноценного разделения чтений и записей. fallback также инвалидирует таблицы из потенциального замыкания. Поэтому библиотечный пробел способен испортить не только результат выражения, но и состояние, на котором строятся следующие запросы. Это ограниченный консервативный приём, а не доказанный эффект конкретного вызова.

Получается цепь усиления: потерян тип обычной операции → generic effects и исключения → раннее исчерпание бюджета → нет результата запроса → нет ID или token для следующего шага → больше неизвестных значений и новых ветвей. Повышение бюджета может отложить остановку, но не восстановит правильный тип, receiver или запрос. Сначала нужны узкие модели поддержанных операций и проверка их стыков, затем — новая политика продолжений.

## 4. Два дефекта самого механизма событий и состояния

### 4.1. Уже достигнутый remote теряется при остановке внутри сервера

В remote_alternative ребро remote добавляется после возврата http_invoke. Обработан JavaThrow, но AnalysisBoundary проходит мимо. Удалённый handler уже имеет executes в трассе, однако соответствующее remote ещё не записано. Это противоречит обещанию сохранять префикс отказавшего или остановленного запроса. [F09](#f09)

Сопоставление request records и executes того же request ID обнаружило 91 такое наблюдение на остановленных альтернативах, 35 различных пар «сценарий + ребро». Большинство компенсирует другая альтернатива union. **Две пары отсутствуют даже в итоговом submission**:

- S6: AdminRouteServiceImpl.checkStationsExists → StationController.queryForIdBatch.
- S7: RebookServiceImpl.getOrderByRebookInfo → OrderOtherController.getOrderById.

Это проверка внутренней согласованности сохранённого прогноза; утверждение о совпадении со скрытым gold не требуется. Событие входа на сервер следует фиксировать в момент установленного входа, отдельно от события ответа. Отказ binding или фильтра до входа остаётся другой ситуацией согласно контракту.

### 4.2. Выбранная единственная альтернатива не переносится обратно

В fork_join после разделения mixed completion может остаться одна выбранная normal- или throw-альтернатива. Перенос окружения выполняется только внутри цикла по alternatives[1:], который тогда пуст. После этого joined_env указывает на original.env, а env.clear() очищает тот же объект. Восстановление читает уже пустую среду. Mutations выбранных receiver/args также не проходят штатный перенос. [F10](#f10)

**Это сильный статический вывод по новой ветке кода; новый контрпример здесь не запускался, проявление в конечном TT score не локализовано.** Существующий тест mixed completion возвращает константы и не читает прежние локальные переменные после catch, поэтому такой дефект может остаться незаметным.

Минимальный независимый контроль: Box.n исходно 0; неизвестное условие задаёт либо n=7 и throw, либо n=9; catch и обычное продолжение читают тот же Box. Должны сохраниться допустимые результаты 7/9 и aliases, а не потеряться локальная переменная. Для одной альтернативы нужна явная операция принятия её состояния; join двух состояний не заменяет эту операцию.

## 5. Request появился; смысловая корректность запроса осталась отдельной проблемой

Общий immutable Request и shared binder полезны. Но интерфейс получает прежние эвристические параметры, а иногда создаёт новый конфликт между ними и UI-производителем. В финальной трассе нашлись следующие случаи. [F11](#f11) [F12](#f12) [F13](#f13)

| Действие | Сохранённый запрос | Диагноз и граница |
|---|---|---|
| S0/5: фильтр оплаченных заказов | parameters: enableStateQuery=true, state=1; в Request.body state отсутствует | Новый omissions-блок конфликтует с NL-фильтром: выбранный unfiltered UI builder не содержит этого поля |
| S4/2: войти с новыми username/password | Отправлены старые предзаполненные реквизиты UI | История новых credentials ищется только в результате регистрации; при неизвестном результате остаётся прежний default |
| S5/4: fewest stops from Shanghai to Nanjing | startPlace=Nan Jing, endPlace=Shang Hai | Эвристика from/to отбрасывает фразу из-за предшествующего with; затем приняты обратные UI defaults |
| S1/13: запись consignment данного заказа | Выбран admin getAllOrders | Лексический top-1 не проверяет требуемый вид результата; подходящий findByOrderId был следующим кандидатом |
| S1/14: запись assurance данного заказа | Выбран список assurance types | Справочник типов смешан с экземпляром записи заказа |
| S2/14: переоформить тот же regular train | Тестовая страница подставляет G1234→G1235, примерный orderId и пустую дату | Не доказана связь UI default с выбранным объектом; исходный UI при пустой дате делает return до AJAX |

В S0/5 ошибка особенно показательна: проверка parameters могла бы пройти, а фактическое тело запроса уже иное. При обычной десериализации этого DTO отсутствие int state означало бы default 0 вместо выбранного 1; непосредственно в трассе доказано исчезновение поля из wire body. Нужно проверять цепь «план запроса → wire body → фактические Java args», а не только внутренний словарь до HTTP-преобразования. [F11](#f11) [F14](#f14)

Новые username/password — уже известный символический пользовательский ввод, даже если успешность регистрации неизвестна. Их следует хранить отдельно от журнала ответов. Неизвестное существование аккаунта не оправдывает переключение на другого пользователя.

В примерах есть константы из исходного UI, но это **не Python-хардкод бизнес-логики Train Ticket**. Проблема — принятие существующего литерала за значение конкретного пользовательского действия без доказанного пути подготовки. Общие правила Java/Spring и реальные source literals допустимы; нужно доказывать их применимость к выбранному запросу.

Для действий without food сохранено конкретное foodType=1 и Bone Soup из UI. Это конфликт, заслуживающий проверки, но я не объявляю его отдельно доказанной ошибкой фактического запроса: в самом JavaScript есть подозрительная truthy-обработка indexOf, и реальный UI тоже может отправлять неверное относительно намерения значение. Требуется восстановить выбранную цепочку UI events. Анализатор должен предсказывать исходный код, включая его ошибки, и показывать конфликт с намерением, а не переписывать поведение под желаемый смысл. [F13](#f13)

### Заголовки и сессия не замкнуты

frontend.sites не переносит config.headers. grounded_request строит заголовки преимущественно из Java-параметров и превращает агрегат @RequestHeader HttpHeaders headers в фиктивный заголовок headers:U. Выражение Authorization из UI не становится полноценным источником начального Request. В сохранённом TT report у всех 103 шагов session неизвестна; ни в одном начальном Request нет authorization. Это не утверждение обо всех внутренних remote-заголовках. [F11](#f11)

Тест Request.http с вручную переданным заголовком проверяет контейнер и binder. Он не проверяет login → сохранение токена UI → защищённый следующий запрос. Нужна именно такая цепочка с успешным и неуспешным входом.

### История получила структуру, но ещё теряет порядок

CollectionRef исправляет свежий singleton и пустой список — это полезный сохранённый результат. Однако provenance сначала пропускает неизвестные IDs и удаляет повторяющиеся identities, а затем выбирает ordinal из сжатого списка. Поэтому статические контрпримеры [Invoice(id=U), Invoice(id=C)] → first и [A,A,B] → second могут дать соответственно C и B. Эти проверки не запускались. Исходная позиция, размер и complete уже представлены в модели, но не используются как обязательные ограничения ordinal. [F21](#f21)

Есть и обратная чрезмерная реакция: неизвестный результат неродственного weather-запроса способен стереть возможность выбрать ранее известный invoice. Это ещё один пример, где новая структура данных полезна, но её семантическое условие применено слишком широко.

## 6. Почему 1 574 passed и независимые проекты не предупредили о провале

Сохранённые успехи реальны в своей области. Я пересчитал графовые показатели 52 строк сравнений по сохранённым ответам и соответствующим версиям oracle; расхождений не найдено. Проблема в том, какие условия эти проверки измеряют. [F14](#f14) [F19](#f19)

| Профиль | Шаги | executes / calls / remote / data | Реальная сила свидетельства |
|---|---:|---|---|
| Синтетический gateway → warehouse | 11 | 9 / 1 / 4 / 4 | Есть состояние, свежий список, отказ и remote; короткие вручную подготовленные исходники |
| Petclinic Customers | 7 | 11 / 7 / 0 / 7 | Реальный ограниченный source-профиль, без межсервисного пути |
| PiggyMetrics account | 3 | 8 / 3 / 0 / 2 | Read → duplicate create → read; предварительная авторизация, успешный Feign путь не проверен |

У синтетики № 23 и № 26 уже выдавали тот же точный граф 18/18. № 27 исправил результаты отдельных шагов с singleton и запретом старого ID — полезное улучшение, которое graph IoU само по себе не замечает.

Но у двух реальных профилей **remote пуст**. Все их 10 шагов не проверяют полноценное межсервисное продолжение, на котором № 27 особенно сильно теряет ответ. Два heldout — одношаговые отрицательные или граничные случаи на уже изученных профилях; после описанного исправления они прошли повтор. У Petclinic это 404 для отсутствующего owner, у PiggyMetrics — HTTP 200 с null. Это регрессионное свидетельство после ремонта, а не новый blind-проект. Исходного traceback первого heldout в пакете нет, подробность NameError известна из документов. [F19](#f19)

У public oracle есть более конкретные пробелы:

- В 5 из 10 шагов expected.arguments пуст, включая обе операции создания. Значение arguments=true в этих строках не проверяет поля DTO.
- В 5 из 10 шагов ignore_result=true. Часть важных ответов и последующих списков не сравнивается целиком.
- compare_public_corpus сравнивает expected.arguments с parameters до Request/binding, а не с wire Request и фактическими Java args.
- Основная проверка state — количество строк и отсутствие unknown_tables. Некоторые значения дополнительно проверяются последующим result, но это не полная проверка полей, identity, aliases и commit.
- Граф сравнивается как union сценария. Ошибочный шаг может быть скрыт совпавшим набором рёбер из других шагов.

Эти ограничения честно описаны в IMPLEMENTATION_REVIEW. Поэтому неверно обвинять авторов в подделке тестов или заявлении полной семантики. Однако метки verified_bounded и passed оказались недостаточным условием для принятия архитектурного сочетания. Нужны отдельные статусы: механизм реализован; компонент проверен; полная цепочка проверена; переносимость проверена; конечный TT граф регрессирует. [F01](#f01) [F15](#f15)

Некоторые тесты не задевают именно опасный стык. Logger проверен в форме log.debug(dto), а не Class.LOGGER.debug(dto). Mixed completion возвращает константы и не читает прежнее окружение. UI/HTTP equivalence содержит простой body, а не token/session/headers. Тест двух deployments с названием о same ID фактически задаёт разные IDs. Это полезные компонентные случаи, но из их числа нельзя вывести устойчивость композиции. [F10](#f10) [F11](#f11) [F21](#f21)

### Что говорят абляции, а чего не говорят

Сравнение observed-union и confirmed-only на тех же сохранённых executions — настоящая экспортная абляция. Confirmed-only теряет ожидаемые рёбра, поэтому условные поддержанные события нужны. Но оба режима исключают static_candidates; эксперимент не сравнивает прежний closure с новой политикой и не проверяет будущий граф после budget stop. [F20](#f20)

Проверка witness подтверждает соответствие экспортированных рёбер событиям, наличие source locations и applied rules, а также корректность имеющихся ссылок на request, context и assumptions. Request может отсутствовать, guards могут быть пустыми. Она не доказывает истинность guard, применимость модели, верность аргумента или полноту продолжения. Ребро может быть хорошо документировано и семантически ошибочно; отсутствующее ребро вообще не предъявляется такому валидатору. [F20](#f20)

## 7. Что в прежней рекомендации нужно исправить

Я сохраняю вывод о целесообразности собственного ограниченного Python-анализатора Java/Spring. В № 27 нет данных, что замена на Joern, CodeQL, WALA или другую готовую основу автоматически восстановит сценарные запросы, состояние и продолжения. Конкретный сбой Class.LOGGER разрешается существенно меньшим изменением. Повторять сейчас большой каталог инструментов было бы уходом от установленной причины.

Пересматриваю приоритеты и форму задания разработке:

1. **Слишком широкое одновременное изменение.** Я перечислил Request, историю, alternatives, opaque effects, события, persistence, донорные изменения и optional experiments. Хотя приоритеты и ограничения были указаны, недостаточно чётко задал прекращение работ после неуспешного первого сквозного сравнения. Список легко превратился в требование реализовать всё сразу. [F18](#f18)
2. **Недооценка цены ужесточения.** Требование показывать только поддержанные события обоснованно, но его результат зависит от покрытия исполнения. Ранняя потеря String/Logger превращает новый чистый экспорт в очень короткий префикс. Я должен был потребовать измерить эту зависимость отдельно, прежде чем менять основную политику.
3. **Слабая спецификация независимой проверки.** Два репозитория и таблица endpoint/args/result/state ещё не означают два полных сценария. Требовались обязательные непустые реальные remote, фактические wire args, известный результат для следующего шага и существенные значения состояния. Пустой expected.arguments и ignore_result должны сразу показывать непройденную часть приёмки.
4. **Неоперационное предупреждение по № 21.** Прошлый отрицательный opaque-experiment уже показывал риск чрезмерной потери состояния. Я это отметил, но не перевёл предупреждение в обязательный запрет интеграции при массовых ложных effects и остановках на известных API.
5. **Неполный единый документ.** Переданный DOCX ссылался на отдельный HTML с подробной картой переноса и глубиной проверки. В пакете № 27 прямо сказано, что этот HTML разработчику не предоставили. Это недостаток передачи моего анализа. Он не доказывает причину score, но карта переноса должна была входить в один самодостаточный документ, как вы и просили. [F01](#f01) [F18](#f18)

Ответственность здесь — за недостаточно узкий и проверяемый следующий шаг. Было бы нечестно обещать, что общий термин «абстрактная интерпретация», ещё одна модель или больше тестов сами по себе исправят ситуацию. Нужно сначала доказать сохранение значений и продолжений на уже поддерживаемом стеке.

## 9. Конкретный следующий эксперимент

Следующий вариант должен отвечать на один вопрос: **можем ли мы восстановить прохождение обычного запроса и перенос его результата, исправляя только доказанные дефекты границ, без бизнес-таблиц и без подмешивания gold?** Ни S0–S7, ни имена сервисов не должны появиться в условиях построителя ответа.

### 9.1. Сначала локализовать изменения на фиксированных входах

Зафиксировать исходный № 27, № 23, source/config/skeleton/context/scenarios и настройки бюджета. Для диагностики execution разрешён явно заданный правильный Request, составленный независимо по исходнику; он используется только в отдельном контрольном режиме. Продуктовый NL-grounder должен оцениваться отдельно и не получать такой oracle.

Последовательность небольших изменений:

|---|---|---|---|---|

Logger | Потерян static field type; остановка до HTTP/DB | project metadata, source_type, общий resolved call contract | bare / Class.LOG / FQN формы; обычный logger сохраняет тот же результат и хвост графа. Сравнение стадий с несколькими одновременно поменявшимися механизмами снова не даст причинного ответа.

Проверка TT после ремонта показывает, прошли ли именно прежние узкие места: Logger перед query/exchange; String через return; загруженный principal. Рост общего числа рёбер принимается только вместе с объяснением новых достигнутых событий и независимыми контрпримерами; вернуть всё старое closure недостаточно.

### 9.2. Затем решить, что делать с настоящей неопределённостью

После A–E повторно сгруппировать причины остановок на контролируемом Request. Разделять: неподдержанную семантику вызова; поддержанную операцию с неизвестным значением; неизвестный receiver; неоднозначный target; допустимый бизнес-отказ; исчерпание вычислительного бюджета. Эти ситуации не должны автоматически получать один и тот же arbitrary Throwable и одинаковый footprint.

A–E не исправляют все унаследованные NL/history-ошибки. Для них сохранить отдельные проверки: символический input регистрации → login с теми же credentials; from/to после with; [Invoice(id=U), Invoice(id=C)] → first; [A,A,B] → second. Неизвестное значение из ошибочного grounding нельзя автоматически считать настоящей неопределённостью исполнения. Исправления этих механизмов идут отдельными патчами после локализации исполнения, а не скрытым дополнением к A–E.

Если остаётся взрыв истинно разных завершений, исследовать ограниченные summaries и раннее объединение совместимых continuations. Для неизвестного внешнего вызова нельзя одновременно обещать точное состояние и полный граф без модели. Неопределённость должна сохраняться в ответе и диагностике; её нельзя выдавать за доказанный normal path. Но потеря типа у поддержанного String также не должна считаться неизвестной внешней семантикой.

Критерий принятия политики бюджета — прохождение независимых цепочек с сохранёнными значениями, отказами и рёбрами при измеренной стоимости. Предельные время/память и численные пороги качества ещё нужно согласовать; здесь новые SLA не назначаются. Уменьшение unknown или быстрое завершение само по себе не является успехом.

### 9.3. Один обязательный полный независимый сценарий до дальнейшего расширения

Нужен закреплённый source-профиль другого реального Java/Spring-приложения, в котором выбранная цепочка действительно проходит между сервисами и обращается к данным. Например, сценарий другого домена должен содержать создание сущности, получение ID из ответа, удалённую проверку доступности, изменение состояния, отказ и последующее чтение. Само наличие репозитория с микросервисами недостаточно: выбранный профиль должен включать этот путь.

Oracle фиксируется независимо до реализации исправлений и сравнивает:

- обработчик и полный существенный wire Request: method, path, query, headers, body, отсутствие/null, identity;
- фактические bound Java args, status и поля результата, используемые дальше;
- значения изменённых записей, commit/rollback и связь полученного ID со следующим запросом;
- события каждого шага и четыре типа рёбер, с непустыми remote и data;
- поведение при invalid input, частично неизвестном списке, неоднозначном действии и ошибке после уже выполненного префикса.

Для исследовательской приёмки нельзя засчитывать обязательное поле через пустой expected.arguments или ignore_result. Игнорируемое поле допускается с явной причиной и не учитывается как проверенное. Один такой успешный профиль открывает следующую итерацию; заявление переносимости требует нескольких независимых предметных областей и действительно отложенных случаев, а не лишь переименований и маленьких snippets.

В рамках текущих ограничений исследуемые приложения запускать не требуется: oracle можно независимо разметить по закреплённым исходникам и предоставленным трассам. Такой oracle должен проверять второй читатель, иначе анализатор и проверка могут повторить одну ошибку. Подготовка качественного oracle здесь дороже добавления ещё одной формы AST, но именно она делает дальнейшее решение осмысленным.

## 10. Что не следует приписывать этому разбору

Этот аудит не доказывает, что все удалённые из № 23 рёбра были правильными; не распределяет 0,46783 потери сайта между Logger, String, budget, grounding и projection; не обещает score после ремонта. Новые контрпримеры из чтения кода не названы выполненными тестами.

Я распаковал архив с проверкой путей, читал код, тесты и документы, сравнивал хеши и безопасно пересчитывал сохранённые JSON. Анализаторы, pytest, локальные модели, JVM, Train Ticket, другие сервисы и сборки не запускались. Промежуточный код стадий и большие исторические трассы отсутствуют, поэтому однофакторную историю по ним восстановить нельзя. ## Приложение B. Дополнительные риски, не объявленные причинами score

Эти случаи выявлены чтением кода. Новые контрпримеры не запускались; они не включаются в объяснение 0,19402 как измеренные причины. Их следует проверять при достижении соответствующего пути, а не превращать в новый обязательный пакет большой версии.

| Риск | Конкретное основание | Независимый контроль |
|---|---|---|
| Неизвестный цикл может дать confirmed event | Engine.add учитывает guard_stack/assumptions; часть loop-пути меняет uncertain без event_guard | unknown while с conditional() и after(); отдельно return внутри тела |
| Nested REQUIRED не передаёт rollback-only | persistence.begin возвращает False при уже открытой транзакции; внутренний boundary не вызывает end | Два Spring beans: Outer ловит RuntimeException из Inner REQUIRED, затем пытается commit |
| uncertain save может прочитать неприсвоенную existing | repository присваивает local только в другой ветке, а использует после обеих | Unknown loop с save: диагностическая неопределённость допустима, Python crash — нет |
| Lazy и обычная materialization могут расходиться | lazy load не проходит тот же materialize_record/attach_collections | Entity с constructor helper, ассоциацией и lazy reference; ID-only read отдельно |
| Dirty checking игнорирует переименование колонок | Сопоставление row keys и Java fields не использует ту же column mapping | @Column с разными именами поля/БД, изменение → flush → следующий read |
| COW cache может пропустить новый alias | TableStore.shared_identities кеширует mutable IDs при той же корневой rows-list | Вычислить cache, добавить row, передать row как input, fork; проверить alias и изоляцию |
| Multi-route handler обходит новый binder | grounded_request возвращает None при нескольких маршрутах; fallback передаёт plain params | Два URL alias одного handler и invalid int/UUID должны одинаково пройти HTTP conversion |
