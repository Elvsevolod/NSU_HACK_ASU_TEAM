# Решение № 3 — stateful-response-propagation

Родитель: решение № 2, scenario-aware-static, score сайта **0,73489**. Score сайта этого варианта — **0,886660**, по скриншоту пользователя от 16.10.2026. Оценённый `solution.zip` сохранён без изменений; в его корне находится `submission.json` с ответами на **S0–S7**.

## Фича

Статический анализатор теперь переносит результаты запросов между шагами: найденный поезд, контакт, созданные заказы, их статусы и запись о багаже. Реализация на Python. Train Ticket, JVM и базы данных не запускаются; внешних LLM API нет. Эталон читает только отдельный оценщик.

Изменения относительно решения № 2:

- Сохраняются тела `Response` / `ResponseEntity` / `HttpEntity`, результаты преобразования JSON и возвращаемые значения вложенных проектных вызовов. HTTP-обработчик уточняется по сервису, методу запроса и пути; учитываются имена `@PathVariable`.
- Исправлен перенос составного `TripId`, полей `@Column`, коллекций JPA и генерируемых идентификаторов. Достоверные записи обновляют независимую копию данных сценария.
- Добавлены модели дат, денежных сравнений, строк, списков и словарей; известные циклы и `switch` разбираются точнее. Комментарии между аргументами больше не превращаются в неизвестный аргумент.
- Сохраняются результаты разных видов расширенного поиска. Ссылка на «самый дешёвый поезд» после других поисков возвращает выбранный результат дешёвого поиска.
- Из административных действий извлекаются явно указанные станции, места, расстояния, тарифы и поезд. ID созданного маршрута передаётся следующим запросам.
- В отчёте есть отдельные рёбра каждого шага, параметры, результаты и состояние заказов. Это позволяет проверять, какая операция добавила спорную связь.

Правила зависят от текста запроса, данных и исходного кода, а не от ID сценария. Готовые рёбра эталона в построитель не добавлялись. Адаптер естественного языка по-прежнему ориентирован на Train Ticket.

## Что проверено в сценариях

**S7.** Создание → оплата → выдача дают статусы заказа `0 → 1 → 2`. После выдачи расчёт возврата, отмена и перебронирование возвращают отказ. Анализ не проходит к ценам и изменению заказа после раннего возврата. При смене получателя багажа сохраняются ID, вес 3 кг и цена; вставка новой записи и повторный запрос цены не достигаются. Отдельный тест с изменением веса подтверждает, что пересчёт цены работает, когда он нужен.

**S2.** Просмотр магазинов станции выбирает обработчик station-food. Сохраняются выбранная еда и два разных заказа. Первый заказ оплачивается и отменяется; для второго выполняется переход с первого на второй класс, возврат разницы и обновление в order-other. Перенос заказа между семействами поездов и внешняя оплата на этом шаге не достигаются. Расчёт возврата первого билета даёт `280.00` по коду приложения.

**S5.** Выбор самого дешёвого поезда сохраняется после поиска быстрых поездов, поездов с минимумом остановок и пересадки. Покупка, оплата, выдача и посадка дают `0 → 1 → 2 → 6`. Для второго участка пересадки Suzhou → Nanjing получается пустой список: в исходном дампе нет подходящего маршрута в этом направлении. Анализатор не добавляет поезд, которого нет в данных.

**S6.** Добавленные администратором станция, тип поезда, маршрут, тариф и рейс становятся доступны следующим шагам. Пассажир находит G9101, создаёт заказ и оплачивает его; итоговый статус заказа — `1`.

Это проверки поведения нашей статической модели по исходному коду и данным. Они не заменяют сравнение графов со скрытыми эталонами. Подробности: [behavior-checks.json](benchmark/behavior-checks.json), [analysis-report.json](benchmark/analysis-report.json).

## Разбор результата сайта

**S7: +0,330 — наибольший прирост.** В отчёте № 2 после покупки, оплаты и выдачи список известных заказов оставался пустым, а статусы ответов были неизвестными. Поэтому анализатор проходил ветки, которые требуют оплаченного, но ещё не выданного билета. В № 3 заказ сохраняется и проходит состояния `0 → 1 → 2`; расчёт возврата, отмена и перебронирование после выдачи отклоняются. На шаге перебронирования число предсказанных уникальных межсервисных связей сократилось с 22 до 1. При обновлении получателя багажа оно сократилось с 2 до 0: ID и вес известны, вставка новой записи и пересчёт цены не нужны. Эти изменения согласуются с ростом оценки. Приписать каждому исправлению отдельную долю прироста без дополнительных загрузок и скрытого эталона нельзя.

**S2: +0,220 — второй по величине прирост.** В № 2 два заказа не сохранялись в состоянии, из-за чего отмена и перебронирование обходили лишние варианты. В № 3 первый заказ оплачивается и отменяется, а второй остаётся отдельным объектом и перебронируется с первого на второй класс. Для более дешёвого билета достигается возврат разницы и обновление заказа в order-other. На шаге перебронирования предсказано 16 межсервисных связей вместо 22. Также исправлен выбор входной точки просмотра еды: магазин станции обрабатывается station-food вместо общего getAllFood. Сайт подтверждает улучшение всего графа S2; вклад отдельных правок пока не разделён.

**S1: +0,146.** Улучшение распространяется на обычную покупку с дополнительными услугами, оплату, выдачу и посадку. В № 3 известный заказ доходит до статуса `6`. Общие исправления передачи ответов и состояния работают за пределами S2/S7, но это не означает, что все ветки дополнительных услуг уже восстановлены точно.

**S5: +0,096; S6: +0,106.** Изначально сильные сценарии также улучшились. В S5 сохраняется выбранный дешёвый поезд после других поисков, затем проходит цепочка до посадки. В S6 созданный маршрут используется при добавлении рейса, а пассажир находит и оплачивает новый поезд. S6 теперь имеет наивысшую оценку — `0,923`; S7 почти сравнялся с ним. Значит, по предоставленным оценкам исправления S2/S7 не привели к ухудшению этих сценариев.

**S3: +0,137, но остаются конкретные проблемы.** Добавление нового контакта в отчёте № 3 возвращает неизвестный результат и предупреждение о неподтверждённой записи. Для покупки на новый контакт передаётся прежний `contactsId`. Запросы «Open the first new order» и «Open the second new order» оба выбирают второй заказ: текущий разбор распознаёт «first order», но не «first new order». На первом заказе также остаётся ответ `Success.But Buy Assurance Fail.`. Это наблюдаемые ограничения нашей модели; их точный вклад в оставшийся разрыв до эталона неизвестен.

**S4: +0,026 — наименьшее улучшение и самый низкий итог, 0,763.** Сценарий начинается с новой регистрации, пустого баланса и нового контакта. В отчёте № 3 `account_id` остаётся неизвестным, создание контакта и заказа не закрепляется как достоверная запись, а список известных заказов остаётся пустым. Затем расчёт возврата и отмена отвечают `Order Not Found`, хотя текст сценария описывает отмену оплаченного заказа. Кроме того, нужно проверить, верно ли выбран входной обработчик внешней оплаты: сейчас выбран прямой payment.pay, а переход с пустого внутреннего баланса требует отдельной сверки с исходным кодом и фронтендом. S4 стал лучше по баллу, но его основная последовательность состояния ещё не восстановлена.

Приоритет следующего разбора: **S4 → S3 → оставшиеся расхождения S2**. Для S4 нужны устойчивые символические значения нового пользователя и контакта, их сохранение между запросами и корректный путь оплаты. Для S3 — выбор первого/второго нового заказа и нового контакта, затем страхование. S7 сохраняем как регрессионную проверку отказов после выдачи. Код решения № 3 после получения оценки не менялся.

## Запуск

Команды выполняются из папки решения. После распаковки ZIP укажите путь к выданному пакету вместо `../../tt-challenge`. Пакет данных в ZIP не включён.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
PYTHONHASHSEED=0 .venv/bin/python -B code/run.py \
  --source ../../tt-challenge/targets/trainticket \
  --skeleton ../../tt-challenge/skeleton/trainticket.json.gz \
  --context ../../tt-challenge/context \
  --scenarios ../../tt-challenge/scenarios \
  --output submission.json \
  --report benchmark/analysis-report.json

.venv/bin/python -B ../../tt-challenge/platform/evaluate_golden.py \
  ../../tt-challenge/gold/S0.json submission.json --json
```

Для одного сценария передайте его файл JSON в `--scenarios`. Анализатор не принимает путь к gold и не импортирует код предыдущих вариантов.

```bash
.venv/bin/python -m pip install pytest==9.1.1
TT_CHALLENGE_ROOT="../../tt-challenge" PYTHONPATH=code \
  .venv/bin/python -B -m pytest code/tests -q -p no:cacheprovider
```

Тесты проверяют условия и ранние возвраты, раздельные заказы, запреты после выдачи, допустимую отмену до выдачи, сохранение и изменение веса багажа, выбор поезда, административные операции и изоляцию данных. Интеграционные прогоны запрещают сетевые соединения и чтение gold; переименование ID S7 не меняет граф. Результаты: [tests.txt](benchmark/tests.txt).

Проверка повторного запуска распакованного кода под другим именем каталога и с другим `PYTHONHASHSEED` сохраняется в [reproducibility.json](benchmark/reproducibility.json). Снимок хешей всех 49 файлов решения № 2 находится в [parent-manifest.json](benchmark/parent-manifest.json).

## Ограничения

- Это ограниченный интерпретатор Java по исходному тексту, не полная реализация JVM. Неизвестные значения, часть библиотечных операций, исключений и потоков управления сохраняют приближения; неизвестные ветки могут давать лишние рёбра. Циклы ограничены 64 проходами, глубина анализа ограничена бюджетом контекстов.
- Успешные проверки отдельных цепочек не доказывают точность всего графа S2, S5, S6 или S7. В отчётах остаются неизвестные условия, в том числе фильтры дат, и предупреждения; некоторые параметры, например номер места и данные новой регистрации, не восстановлены полностью.
- Даты, учётные записи и часть значений по умолчанию относятся к выданному контексту. Для часов без указанного времени используется 15.09.2026, 12:00. Административные часы привязаны к дате поездки 01.10.2026. Произвольные формулировки и даты требуют развития адаптера.
- Сохранение объекта и повторное чтение учитывают используемые здесь отображения JPA, но не все возможности ORM и SQL. Транзакции и конкурентное исполнение не моделируются полностью.
- Остаточные ошибки S0 сохраняются. Код не дополнялся готовыми связями из эталона ради увеличения этой метрики.

Решение № 2 сохранено без изменения кода, ответа, архива и метаданных. Пользователь загрузил решение № 3 и предоставил его оценки. После этого обновлены README и метаданные, а папка переименована в `0.886660_stateful-response-propagation`.

Оценённый `solution.zip`, код и `submission.json` не изменялись. README и метаданные внутри архива отражают состояние до получения оценки; актуальные показатели находятся в README этой папки и `benchmark/site-score.json`.
