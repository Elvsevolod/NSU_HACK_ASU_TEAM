# № 29: почему оценка остаётся слабой и что делать дальше

**Дата проверки: 18 октября 2026 года.** Предмет разбора — `solution_29_after_review_analysis.zip`, его текущий код, историческая отправленная посылка и сохранённые измерения относительно № 28. Все результаты ниже собраны в этом документе. Обозначение **U** означает неизвестное значение в модели анализатора.

## Основной вывод и выбранное направление

**№ 29 нужно сохранить как рабочую диагностическую базу. Следующая основная итерация — исправить семантику `HashSet`, затем научиться проходить доказанно независимые от порядка циклы `Map` без потери всех известных объектов. Принимать эту работу следует по восстановленной передаче данных между запросами.** Отдельным небольшим изменением можно восстановить уже локализованный переход известного login-ответа в предусмотренные исходником storage-записи и следующий header; смешивать его результат с коллекционным экспериментом не следует.

№ 29 принёс реальную пользу: сохранённая оценка сайта выросла **с 0,27421 до 0,36114**, восемь оплат вернулись к полноценному платёжному обработчику, поиск проходит прежнюю границу JSON-массива, существующий пользователь получает известный токен. Все семь сохранённых оценок скрытых сценариев выросли. Поэтому считать эту итерацию бесполезной было бы неверно. Однако **полная цепочка сценария всё ещё разрывается в нескольких конкретных местах**, а локальные положительные тесты обходят часть этих переходов. [Оценка сайта][site29], [пересчёт измерений][metrics29], [сравнение запросов][requestdelta].

Самые существенные новые результаты аудита:

- `HashSet` реализован через список с безусловным `append`: в реальный batch-запрос уходят дубликаты. Это ошибочная конкретная семантика, а не просто недостаточная точность.
- Неопределённый порядок `Map` перебирается вариантами; при исчерпании лимита расширяется до неизвестности вся достижимая локальная куча. Известные параметры последующих запросов теряются даже при фактически неработающем теле фильтрующего цикла.
- Восемь login-шагов уже имеют известный успешный токен, но сохранённое browser storage остаётся пустым: экстрактор не присоединяет AngularJS `.success(...)` к исходному `$http(...)`.
- Независимый Petclinic показывает потерю идентичности изменяемой сущности: корректный `PUT /owners/1` заканчивается сохранением объекта с неизвестным ID и появлением лишней строки. Значит, проблема сохранности значений выходит за пределы Train Ticket. [Коллекции][engine], [трасса поиска][search29], [login][login29], [Petclinic][petclinicreport].

В моей предыдущей рекомендации первым приоритетом были два отдельных ремонта — ранжирование и JSON-массив — с последующим решением по первой оставшейся потере. Эти ремонты выполнены; связанный массивный путь потребовал дополнительных исправлений. Но в № 29 работа снова разрослась до большого набора локальных пунктов, а строгая независимая проверка всей нужной цепочки осталась частичной. **Мою следующую рекомендацию тоже нужно считать проверяемой гипотезой с условием остановки, а не новым обязательным списком возможностей.** Конкретное задание на следующую итерацию приведено в разделе 8. [Предыдущий разбор, разделы 7–8][review28], [требования № 29][requirements29].

## 3. Подтверждённые причины оставшихся ограничений

### 3.1. `HashSet` исполняется как список с дубликатами

`Engine` создаёт стандартный no-argument `HashSet` как `JavaList` с `flavor="HashSet"` — `engine.py`, строка 2592. Последующий `add` доходит до строки 3111: выполняются `append` и безусловный `return True`. `size` использует длину списка; `new ArrayList<>(set)` копирует это же содержимое. Отдельный dispatcher `java_lists.py` не реализует для этого flavor уникальность элементов. Это поведение унаследовано от № 28. [Конструкторы и native-вызовы][engine], [List dispatcher][javalists].

В исходном `BasicServiceImpl.queryForTravels`, строка 134, создаются три `HashSet<String>`. По сохранённой трассе S1/2 в аргументе station lookup находятся **12 имён с повторениями**, хотя уникальных имён **два**; в train-type lookup — **6 значений**, хотя уникальных имён типов **три**. Речь об actual аргументах последующего repository-вызова, а не о предположении по названию контейнера. [Исходный поиск][basic], [точная выжимка трассы][search29].

Контракт Java 8 требует уникальности по `equals`, возврата `false` при повторном `add` и не устанавливает порядок обхода HashSet. Поэтому механическая замена JavaSet на Python `set` также недостаточна: нужны Java-тип и равенство, а для пользовательских объектов — поддержанный `equals/hashCode` либо явная неопределённость. [Oracle: HashSet, проверено 18.10.2026](https://docs.oracle.com/javase/8/docs/api/java/util/HashSet.html).

**Минимальный независимый контрпример — предложен, не запускался:**

```java
Set<String> codes = new HashSet<>();
boolean first = codes.add("A");
boolean second = codes.add("A");
int count = codes.size();
// first=true, second=false, count=1;
// new ArrayList<>(codes) содержит один элемент.
```

Этот дефект нужно исправить до доказательств более сложных операций над множествами. Исправление не обязано само устранить Map budget: после дедупликации в соответствующей Map всё равно остаются несколько разных ключей. Скрытый вклад дубликатов в score не измерен.

### 3.2. Неизвестный порядок обхода уничтожает слишком большую часть состояния

В final S1/2 прежних opaque `getName` и scalar-coercion уже нет. Поиск доходит до `BasicServiceImpl.queryForTravels`, строка 219: перебираются группы типов поездов; из `avaTrips` удаляется группа, только если `trainTypeMap.get(ttype)==null`. В просмотренных альтернативах Map содержит известные записи типов, а выполненная проверка для первого ключа возвращает `false`. Следующий выбор порядка расходует бюджет. [Исходник][basic], [условия и решения поиска][search29].

Механизм точно локализован: `map_views.iterator_next`, строка 31, выбирает очередной ключ; `Engine.choose_map_order` передаёт выбор общему механизму альтернатив. При невозможности продолжить `view_items` вызывает `widen_map_iteration`, строка 3195. В строке 3199 выполняется **`for value in owned_objects(env): widen(value)`**, затем fallback всего метода. Это расширяет известные `routeIds`, `avaTrips`, response и другие достижимые объекты независимо от того, мог ли именно этот цикл их менять. В одной из downstream-альтернатив `findByIds` уже получает шесть U, тогда как таблицы остались известными. [Map iterator][mapviews], [widening][engine], [трасса][search29].

Признать неизвестность порядка `HashMap` корректно: API не обещает стабильного порядка. Ошибка инженерного решения заключается в грубости дальнейшего анализа. Для цикла с доказанно ложными guards не требуется перечислять перестановки, чтобы установить отсутствие изменений. Для коммутирующих фильтров можно вычислять совокупность удалений, если отдельно доказаны условия применимости. Это вывод о способе улучшения, пока без измерения реализации. [Oracle: HashMap, проверено 18.10.2026](https://docs.oracle.com/javase/8/docs/api/java/util/HashMap.html), [текущая реализация][engine].

Уже существующий `commuting_map_copy`, строка 3216, узнаёт лишь узкую форму `dst.put(k, source.get(k))`. Она не покрывает нынешний фильтр. Продолжение должно использовать такую же осторожную границу: стандартные поддержанные контейнеры, известные ключи и membership, отсутствие скрытых записей, наблюдения порядка и неучтённых исключений. Произвольная сортировка HashMap или единственный порядок Python-словаря не доказывают поведение Java.

**Почему четыре `returned` не означают, что поиск исправлен.** В текущих восьми альтернативах четыре дают `status=1, data=[]`, четыре останавливаются по budget. После widening условие `avaTrips.size()==0` становится неизвестным; replay допускает ранний return с отказом из Basic. Travel получает этот отказ и возвращает заранее созданный пустой список, который внешний метод оборачивает в status=1. Например, путь виден в `/scenarios/S1/steps/1/alternatives/0/path_conditions/47`, затем `/48`. Это конкретный результат одной расширенной альтернативы. Он не доказывает пустоту реального поиска; одновременно наличие других неизвестных альтернатив не позволяет объявить всё объединение доказанно неправильным именно по этому пустому ответу. [Полный report][finalreport], [разбор причинной цепочки][search29].

**Независимый контрпример для следующего ремонта — предложен, не запускался:** несколько SKU сгруппированы по категориям; каталог содержит каждую категорию; цикл удаляет товары только при отсутствии категории. Результат обязан сохранить исходное membership при любом порядке категорий. Отрицательные варианты: ранний `return` по первому ключу, remote внутри тела, запись в общий счётчик, alias на перебираемую Map, неизвестное равенство ключей. На них оптимизация должна либо обосновать поведение отдельно, либо отказаться от сокращения вариантов.

### 3.3. Известный токен не попадает даже в выбранную admin-сессию

Все девять login-шагов final выбирают `adminlogin.js`; в восьми есть известный успешный token, исключение — вход нового пользователя S4/2. Однако **во всех login-альтернативах `state_after.browser.storage={}`**. Более широкий пересчёт показывает: во всех 103 шагах начальное session storage и итоговое browser storage пусты; у 65 начальных Request есть Authorization, но известных его значений — ноль. Это счётчик сценарных входов, не всех внутренних remote headers. [Login witnesses][login29], [агрегация][requestcounts].

В исходном `adminlogin.js`, строка 9, используется `$http({...}).success(function(data, ...){...}).error(...)`. При `data.status==1` callback записывает `admin_name` и `admin_token`. `Frontend.__init__` в `frontend.py`, строка 626, ищет только `config.get('success')`, затем извлекает effects из этого свойства. Цепочный `.success(...)` не связан с request; `apply_response`, строка 1464, перебирает пустой список эффектов. Этот участок унаследован от № 28; новый frontend diff добавляет предупреждение о missing storage. [Исходный callback][adminlogin], [экстрактор и применение ответа][frontend].

Поэтому объяснение «admin UI пишет другие ключи, чем читает passenger UI» описывает следующий возможный разрыв, но пропускает более ранний: анализатор пока не выполняет даже предусмотренную запись admin-ключей. Приложенная версия AngularJS — **1.5.8**; её локальный `angular.js`, строка 11473, определяет legacy `promise.success` и передаёт callback именно `response.data`, status, headers и config. Этот контракт прочитан в поставленных исходниках, без запуска браузера. [AngularJS приложения][angular], [подключение библиотеки][adminhtml].

Тест `test_jjwt_authenticated_requests.py`, строка 83, вручную ставит token в следующий Python Request. Он полезно проверяет JWT/filter, но обходит эту ошибку. Маленький end-to-end regression с token headers использует jQuery `success:` и тоже не покрывает выбранную Angular-форму. [JJWT-тест][jwttest], [проверка jQuery][headertest].

Следующее ограниченное изменение здесь понятно: поддержать именно распознанную цепочку legacy AngularJS, связать callback с конкретным AST-узлом `$http`, сохранить его guard и пути ошибок. Не переносить произвольно свойства ответа в похожие storage-ключи. Не считать обычный `.then` эквивалентом `.success`: форма аргумента зависит от контракта вызова.

### 3.4. Actor теряется до получения credentials

В S6/1 сценарий требует вход администратора, но actual body использует глобальные пассажирские credentials из контекста; actor остаётся U. В S6/7 формулировка входа пассажира тоже не меняет actor. `actors.py`, строка 10, распознаёт только префикс `As <role>,`. `read_static_context` в `contracts.py`, строка 111, кладёт credentials в общие facts, а `_bind`, строка 649, подбирает их по имени поля. Source/контекст различают пассажира и администратора. [Сценарий S6][s6], [контекст][ttcontext], [actor parsing][actors], [binding][contracts], [инициализация пользователей][authinit].

Добавленная в N нормализация administrator→admin помогает ranking. Она не нормализует всю идентичность в `ScenarioState.select_actor` и не задаёт область credentials. В этой трассе source login после authentication создаёт token для фактически выбранного пользователя; желаемую административную identity это не доказывает. Если контекст не даёт доказанных credentials администратора, их нужно оставить неизвестными с причиной, а не брать пассажирский default или автоматически объявлять исходный init-пароль действующим. [State][state], [login witnesses][login29].

Полезное исключение из старой критики: в S4/2 новые username/password действительно приходят через `input_journal` из ввода S4/1. Это сохранённый механизм № 28. Но факт переноса введённых значений не доказывает успешную регистрацию в БД — результат самой регистрации здесь неизвестен. [Binding, `_bind`][contracts], [выбранные цепочки][requestevidence].

### 3.5. Правильный платёжный entry всё ещё не даёт конкретного платежа

Во всех восьми исправленных NL-оплатах actual `PaymentInfo.orderId` и `tripId` неизвестны. Всего 88 альтернатив: **44 возврата `Payment Failed, Order Not Exists` и 44 budget stops; `Payment Success` нет**. При этом видимое `body={}` нельзя читать как доказательство отсутствия полей: `body_properties.info` помечает orderId/tripId присутствующими, но неизвестными. [Сводка оплат][paymentsummary], [сохранённые Request witnesses][paymentwitnesses].

Успешная explicit-проба — другой эксперимент: `run_tt_causal_probes.py`, строка 23, берёт существующий неоплаченный заказ из начальной БД и вручную задаёт orderId, tripId, userId, price. Сохранённый результат полезен: известный заказ проходит оплату и записи, отсутствующий отказывается до записей. Но он не проверяет создание заказа из NL, выбор строки и передачу результата предыдущего шага. [Производитель probes][probecode], [сохранённые probes][probes].

Есть и отдельная граница исходного приложения. Выбранный UI посылает только orderId/tripId. `InsidePaymentController` не добавляет userId; `InsidePaymentServiceImpl.pay`, строка 48, читает его из body и затем использует при работе с балансом. Поэтому даже восстановленные orderId/tripId не дают права заявить успех того же пути, что у пробы с добавленным userId. Нужны два контроля: **точный source UI payload** и **отдельный явно заданный полный HTTP payload**. Предсказывать обоснованный отказ приложения — тоже часть задачи. [Producer][paymentui], [контроллер][paymentcontroller], [consumer][paymentservice].

### 3.6. Petclinic подтверждает независимую потерю состояния

В приложенном legacy-профиле Petclinic шаг 4 отправляет правильный `PUT /owners/1` с новыми полями; `findById` получает 1. Но `save` получает Owner, у которого все поля, включая ID, неизвестны. После обновления во всех семи альтернативах таблица содержит три строки вместо двух; следующий read возвращает прежние поля исходной строки. В последнем шаге остаётся дополнительная generated-строка с неизвестными свойствами. Это наблюдаемое расхождение состояния, даже если общий граф содержит ожидаемый data edge `save`. [Petclinic report][petclinicreport], [сравнение legacy][legacycomparison].

В той же трассе перед save есть opaque-вызов `ToStringCreator.append` из `Owner.toString`, с несколькими heap roots и неразрешённым global footprint. В исходном `OwnerResource.updateOwner` присутствует логирование изменённого объекта; `Owner.toString` использует Spring `ToStringCreator`. Это **сильная гипотеза о причине потери полей**, но её вклад не изолирован запуском абляции. Минимальный контроль: load entity → change field → source formatting/logging → save → read; парный вариант меняет только наличие форматирования. [OwnerResource][ownerresource], [Owner][owner], [Petclinic report: `/scenarios/clinic-journey/steps/3/alternatives/0`][petclinicreport].

Такой пример нужен для проверки области эффектов. Просто объявить все методы `append` чистыми или отключить source `toString` нельзя: пользовательское форматирование может выполнять реальные вызовы. Нужен точный библиотечный контракт для распознанного `ToStringCreator` и отдельное сохранение source callbacks, либо корректно ограниченное изменение достижимой области состояния.

### 3.7. Где нужно различать ошибку движка и ошибку приложения

После N шаги S2/4 и S3/4 про food stores получают две равнооценённые service-гипотезы. Обе теряют явно указанную станцию Suzhou: POST получает неизвестный список имён, GET — неизвестный path segment. Это конкретный пробел semantic binding. Но GET source объявляет `{stationId}` при неявном `@PathVariable String stationName`: HTTP binding failure имеет основание в самом приложении. Исправлять его подменой общих Spring-правил нельзя. Правильность прежнего composite UI-входа против новых direct service-входов без определённого UI-event также не установлена. [Food source][foodcontroller], [выбранные Request][requestevidence], [binding][contracts].

Так же нельзя считать всякое отличие legacy gold доказанной ошибкой. Старый Piggy oracle требует HTTP 500 для повторного аккаунта, а текущий source выбрасывает `IllegalArgumentException`, обрабатываемое `ErrorHandler` с HTTP 400. Сохранённое поведение № 29 согласуется с этим source. В Petclinic «лишние» `toString/getId/getLastName/getFirstName` имеют source-основание в логировании. Эти эталоны нуждаются в версионированном пересмотре; удаление указанных событий ради старого IoU ухудшит связь ответа с исходниками. [Piggy ErrorHandler][piggyerror], [Piggy service][piggyservice], [legacy comparison][legacycomparison], [Owner source][owner].

## 4. Насколько сильны новые проверки

### Что подтвердил независимый Piggy-профиль

Реальные 49 Java-файлов основного Piggy-профиля совпадают с № 28; v2 oracle и старые checkers сохранены побайтно. В v3 прежние semantic edges сохранены, а projected edges отдельно исключают предусмотренные контрактом reflection-события. Проверены исходные декларации и хеши; в сохранённых основных 8 и дополнительных 3 шагах совпадают обе проекции четырёх типов рёбер. К уже существовавшим строгим проверкам wire, аргументов и состояния добавлена отдельная проверка semantic relations и значений/аргументов JSON callbacks. Это полезное развитие доказательств, не новый независимый проект. [Пересчёт корпуса][corpus29], [semantic projection checker][semanticchecker], [review v3][piggyreview], [правило организаторов: REFERENCE, строка 64][ttreference].

V2 исправлялся после начала прежних runtime-работ A/C; v3 учитывает предыдущую критику проекции. Это версионированный source-only review, а не новый holdout, замороженный до всей разработки. Важно сохранить эту хронологию вместе с точными хешами, не отвергая полезный независимо обоснованный пересмотр проекции. [Oracle v3][piggymainoracle], [review v3][piggyreview].

Границы сохраняются. В основной проверке callback receiver/trigger и полная хронология не проверяются исчерпывающе. OAuth context передаётся готовым, полноценный login/UI/NL этим профилем не закрыт. В прогонах path limit 1/4/8 каждый шаг имеет одну альтернативу, а сохранённые шаги совпадают целиком за исключением `path_limit`: это стабильность простого пути, не нагрузка на планировщик. Шестнадцать mutation-проверок показывают чувствительность checker к выбранным повреждениям; они не измеряют полноту генератора. [Checker][semanticchecker], [проверка корпуса][corpus29].

### Document journey — хороший синтетический контроль, с конкретными пробелами

Новый пример проходит **список → выбор первого документа → approve с remote 503/fallback → повторное чтение** и через explicit HTTP, и через настоящий NL pipeline. В сохранённых значениях ID `D7` и revision 7 переходят в следующий запрос, затем в БД сохраняются revision 8 и `approved=true`. По шагам E/C/R/D составляют **3/1/1/1 → 4/1/2/1 → 3/1/1/1**; есть отдельный explicit stale-revision regression test. Здесь непустые remote/data и изменение состояния действительно присутствуют. [Fixture/test][documenttest], [export/checker][documentchecker], [сохранённый NL][documentnl], [проверки][documentchecks].

Но пример состоит из небольших специально написанных Java/UI-файлов и одного документа; новая реальная document-система не подготовлена. Кроме того, NL report остаётся `analysis_status="partial"` с предупреждением о неполной JSON projection для codec failures. Экспортирующий checker проверяет граф и result, а не весь wire, actual args, состояние и границу диагностик. Это не отменяет наблюдаемого успеха перечисленных величин, но ограничивает заявление о полноте сценария. [Требование R11][requirements29], [NL report][documentnl], [checker][documentchecker].

Недорогой пробел самого checker: `run_document_journey.py`, строки 54 и 56, сравнивает Python-значения обычным `==`; поэтому подмена `true` на `1` в result не будет различена этим предикатом. В реально сохранённом результате boolean корректен; речь о **предложенной, не выполненной мутации проверки**. Строгое сравнение JSON-типов уже есть в Piggy-проверках — его стоит использовать и здесь. [Document checker][documentchecker], [Piggy equal/typed_value][piggychecker].

## 5. Почему процесс по-прежнему даёт слабый общий результат

**Первая причина — незамкнутые переходы значений.** Исправление обработчика не создаёт потерянный ID. Успешное JWT-подписание не выполняет клиентский callback. Корректный array decoder не гарантирует правильный Set и сохранность Map-loop state. Эти утверждения в № 29 подтверждаются разными точными witnesses; дальнейший шаг сценария наследует каждую потерю. Поэтому таблица «механизм реализован» должна сопровождаться конкретным переходом `producer → значение → consumer`.

**Вторая причина — разные свойства ошибки сливаются в U.** Ошибочная уникальность Set, неизвестный порядок Map, неизвестная принадлежность элемента, возможное исключение и неизвестная область записи требуют разных действий. В № 29 частичные DTO и repository wrappers уже улучшены, но целое окружение цикла всё ещё может расширяться целиком. Более частый downstream `String2Lower` не становится от этого основной причиной: ему часто уже передан потерянный вход. [Диагностика][diagnosis29], [Map widening][engine].

**Третья причина — обход интеграции в положительных тестах.** Реальная payment-проба вручную задаёт исходный заказ; login-тест вручную переносит token; Piggy получает готовый auth context; синтетический document case имеет один элемент и одну альтернативу. Каждый контроль нужен для своего слоя. Положительный вывод о полном продукте требует второй проверки, где недостающий переход выполняет сам анализатор. [Probes][probecode], [JWT tests][jwttest], [Piggy runner][piggyrunner], [document checker][documentchecker].

**Четвёртая причина — критерий закрытия задачи остаётся слишком локальным.** Полный граф сайта агрегирует исполнение многих зависимых шагов; число unit-тестов, accepted-format и отсутствие одного warning не измеряют это свойство. В требованиях № 29 границы честно признаны — особенно R6/R11/R12. Следующий управленческий шаг: выбрать одну цепочку и заранее определить известные значения, события и допустимые неопределённости на каждом переходе. [Требования][requirements29], [финальная приёмка][acceptance].

В production `code/analyzer/` выполнен дополнительный поиск точных маркеров Train Ticket, `ts-basic-service`, `InsidePayment`, `fdse` и отдельных идентификаторов S0–S7; совпадений нет. Это ограниченный отрицательный результат поиска, не доказательство отсутствия всякого предметного допущения. Наиболее существенные найденные ошибки относятся к общим правилам и их границам. Правило известной версии JJWT или стандартного Java HashSet допустимо как библиотечная модель; константы в независимом fixture допустимы как тестовые входы. Эвристика «имя начинается с get — значит не пишет» требует отдельного доказательства независимо от отсутствия названий TT. [Область проверки][changemap], [library versions][libraryversions], [resource effects][resourceeffects].

Существуют и дополнительные статически найденные риски новых общих правил. Они **не объявляются причиной текущего hidden score и не должны все войти в следующую реализацию**:

| Механизм | Ограничение доказательства | Предложенный отрицательный контроль, не запускался |
|---|---|---|
| `resource_effects.possible_writes`, строка 21 | Repository-операции с `find/query/get/...` считаются чтениями по префиксу при ряде условий | `@Procedure` с именем `getNextNumber`, которая меняет БД; имя не доказывает отсутствие записи |
| `absence_contracts.empty_equivalent`, строка 42 | Наблюдения DTO ищутся через имена формальных параметров; alias/escape не замыкается | Alias DTO различает null и пустую строку после прямого `StringUtils.isEmpty(input.getChallenge())` |
| Startup singleton и join | После ветвления требуется сохранить единую идентичность receiver и cached bean; текущие пути join рассматривают их раздельно | `@PostConstruct` задаёт поле; ветка меняет его; затем общий setter; следующий Request читает ровно итоговое значение |

Для первых двух рисков найдены конкретные недостаточные условия проверки в коде; для singleton это более слабая гипотеза о сохранности alias через join. Реального воспроизведения этих трёх контрпримеров в данном аудите нет. Они подходят для очереди проверок границ, когда затрагивается соответствующий модуль. [Resource effects][resourceeffects], [absence proof][absence], [bean lifecycle][beanlifecycle], [join в Engine][engine].

## 6. Выбор архитектурного продолжения и внешние подходы

### Реалистичные варианты

| Путь | Что даёт | Стоимость и риск | Решение сейчас |
|---|---|---|---|
| Дальше расширять № 29 большим пакетом возможностей | Новые частные покрытия | Смешивает причины улучшения/регрессии; цепочки остаются непроверенными | Приостановить такую форму развития |
| **Ограниченно заменить слабую семантику коллекций внутри № 29** | Исправляет конкретные неправильные аргументы и локализованный источник потери данных | Средняя; нужно выдержать Java equality, order, aliases, exceptions | **Предпочтительный основной эксперимент** |
| Отдельно починить source callback и actor/session | Есть известный token и точный неисполненный source effect | Локальная/средняя; поддержка всех форм JavaScript не требуется | Два самостоятельных изменения после/параллельно основной работе, со своей приёмкой |
| Возврат № 23 или № 5 целиком | Более высокий исторический score | Не доказывает переносимость и правильность state; смешивает старые проекции и семантические допущения | Сохранить неизменными как сравнение, без автоматического выбора базой |
| Новый continuation/worklist core | Может уменьшить повторение работы и лучше сохранять normal/throw | Высокая; затрагивает state ownership, join, effects и экспорт | Проверять отдельным прототипом только при неуспехе ограниченного коллекционного эксперимента |
| Заменить весь анализ готовым движком или локальной LLM | Потенциально меняет извлечение/grounding | Очень высокая интеграционная неопределённость; в № 29 нет нового сравнительного измерения | Сейчас нет оснований начинать полную замену |

Аргумент в пользу № 29 — наличие работающих исправлений и достаточных traces для следующего контролируемого изменения. Номер версии и 1693 теста не являются самостоятельными основаниями. Объединение со старой веткой потребует сопоставлять носители значений, state ownership, нормальные/исключительные завершения и правила проекции; копирование большого `engine.py` не является безопасным переносом полезных частей.

### Что дают первичные внешние источники именно этому решению

В этом аудите интернет-поиск использовался точечно. Проверены Java 8 HashSet/HashMap и исследование **Servois — “Automatic Generation of Precise and Useful Commutativity Conditions”**, Bansal, Koskinen, Tripp, TACAS 2018. Дата проверки — **18.10.2026**. Это проверка доступных первичных материалов, а не заявление о появлении нового движка в 2026 году.

Servois рассматривает условия коммутативности операций по логическим спецификациям абстрактных типов данных с помощью SMT. Для нас полезен принцип: сокращать варианты, когда установлено, что их перестановка не меняет наблюдаемый результат. У него на входе формальные спецификации; он не извлекает готовую семантику Spring/HTTP/NL-сценария из нашего ZIP. Поэтому непосредственное внедрение Servois не обосновано: сначала достаточно ограниченного доказательства над уже поддержанными контейнерами. Лицензия, нынешние зависимости, память и цена интеграции его реализации в этом аудите не измерялись. [Статья, abstract](https://arxiv.org/abs/1802.08748), [полный PDF](https://arxiv.org/pdf/1802.08748).

Joern, CodeQL, YASA, Infer, WALA/Soot, Mopsa и Gillian **не прогонялись** на № 29; нового глубокого сравнительного аудита всех этих проектов здесь нет. Старый каталог не превращается в результат такого прогона. Конкретные нынешние дефекты находятся уже после извлечения нужных фактов: исходный `HashSet` известен, Map-loop прочитан, `$http.success` виден в source. Замена поиска символов или общего графа зависимостей сама по себе не задаёт недостающие runtime/client-контракты. Более глубокий внешний компонент имеет смысл отбирать лишь для установленной границы, с парной проверкой того же входа.

Локальная модель могла бы позднее участвовать в извлечении actor или предложении Request-кандидатов. Её подсказка не должна создавать отсутствующие credentials, ID заказа, storage effect или успешную ветвь. В № 29 отсутствует новое измерение, которое показывало бы, что модель решает найденные разрывы быстрее и экономнее детерминированного ремонта. Новую модель в следующую обязательную итерацию я не включаю.

### Какие границы архитектуры действительно нужны

| Обязанность | Необходимое представление | Зачем оно нужно в найденных случаях |
|---|---|---|
| Извлечение source-фактов | Разрешённый Java-тип/библиотека, форма контейнера, route, DTO, AST-origin callback | Отличить HashSet от List, Angular legacy callback от произвольного метода с тем же именем |
| Сценарий и вход | Actor, источник credentials, кандидаты event/Request, явные literals, ссылки на прошлые результаты | Не терять администратора, станцию или источник orderId; не выбирать произвольно при неоднозначности |
| Значения и исполнение | Тип и nullability, известное membership, порядок отдельно от membership, aliases, normal/throw, область возможных записей | Не превращать неизвестный порядок в неизвестность всех значений; сохранить ID сущности через сторонний вызов |
| Межшаговое состояние | DB, singleton state, browser storage на actor/client, подтверждённые результаты и введённые значения | Токен и созданные ID должны попадать к реальному consumer по доказанному пути |
| События и проекция | Source/callback/HTTP/datastore events, причина и уровень определённости каждого экспортируемого ребра | Разделить реальные события и контракт TT-проекции, не маскировать проблемы состоянием графового множества |

Отдельный новый IR ради этой таблицы не требуется. Значительная часть представлений уже существует; нужно довести их совместимость на конкретных переходах. Для коллекций первым шагом достаточно сохранить **membership независимо от order**, корректное равенство и write footprint. Для frontend — происхождение callback и фактические записи. Полную JVM или универсальный JavaScript runtime этот план не предполагает.

## 7. Приоритетный план проверок и изменений

### Основная следующая итерация: один коллекционный эксперимент, два патча

**Патч C1 — семантика ограниченного стандартного Set.**

- **Проблема:** duplicate `add` возвращает true и увеличивает размер; actual batch-аргументы содержат дубликаты.
- **Механизм:** выделить корректное представление Set либо достаточно строго разделить поведение существующего носителя. Сохранять Java-типы элементов, membership, cardinality и неизвестный порядок. Начать с доказанно стандартного HashSet и известных строк; границу остальных overload/equality явно обозначить.
- **Затрагивается:** native constructors в `engine.py`, коллекционные carriers/dispatchers, преобразование Set в List, iterator и его order-представление.
- **Независимая проверка:** повторное добавление, результат add, size, contains/remove, null и копирование в список; затем source HTTP batch по повторяющимся категориям в другой предметной области. Проверять actual args, а не только финальное множество рёбер. Пользовательский Set/equals и неизвестный ключ — отрицательные контроли.
- **Приёмка:** все размеченные concrete membership/boolean/size верны; стандартный JavaSet не создаёт дубликатов; порядок не придуман. В TT аргументы найденных station/type lookup содержат соответственно два/три уникальных известных имени при том же исходном Request. Остальной результат поиска фиксируется честно, даже если Map-barrier остаётся.
- **Риски и стоимость:** средняя. Нельзя слить Java boolean/integer равенство, потерять aliases или объявить порядок определённым. Сравнить с № 29 все изменившиеся Request/args, граф и состояние; объяснить изменения, не требовать прежнего ошибочного дублирования.

**Патч C2 — ограниченное доказательство no-op цикла Map и сохранение области состояния.**

- **Проблема:** известные ложные guards не спасают heap от `widen_map_iteration`; последующие route IDs теряются.
- **Механизм:** первым поддержать случай, где для каждого известного элемента guard доказанно false; его вычисление чистое, не бросает исключений и не содержит source callbacks, требующих событий исполнения. Затем, только при необходимости, добавить доказанно коммутирующее удаление. Если область возможных записей независимо доказана, расширять лишь её с учётом alias. Если footprint неизвестен, сохранять консервативную границу: перечень видимых присваиваний не доказывает отсутствие скрытых эффектов.
- **Затрагивается:** `map_views.py`, `view_items`, `widen_map_iteration`, summary/proof рядом с `commuting_map_copy`, учёт normal/throw и heap footprint. Извлечение новых маршрутов и NL-ranking не входят в патч.
- **Независимая проверка:** каталог/склад с несколькими категориями; все категории найдены, часть отсутствует, predicate неизвестен, порядок наблюдается через ранний return, внутри цикла есть remote или исключение, есть aliases. Нужна цепочка list/filter → выбранный ID → update → reread, с непустыми remote/data и отдельно проверенным отказом до записи. Синтетический контроль обязателен для локализации; самостоятельный реальный source-профиль нужен для заявления о переносимости.
- **Приёмка:** на поддержанном no-op пути известные membership, поля и результат сохраняются независимо от перечисления порядка. Actual downstream Request получает ID из результата; не появляется ложная пустота или успешный результат с выдуманными полями. Отрицательные случаи сохраняют реальные альтернативы/границы. По TT повторить тот же explicit search и полный NL search, показать первую оставшуюся потерю, если она есть.
- **Риски и стоимость:** средняя/повышенная. Опасны скрытые вызовы equality, source overrides, alias на контейнер и order-sensitive side effects. Первую версию proof стоит сознательно ограничить; отказ от оптимизации должен быть явным.

**Условие остановки.** Если C1/C2 прошли независимые контроли, но поиск всё ещё не даёт пригодного результата, не расширять патч автоматически. Зафиксировать ближайшую новую потерю и проверить, относится ли она к неподдержанной библиотеке, идентичности состояния или исчерпанию продолжений уже при корректных значениях. Только последняя ситуация обосновывает следующий отдельный эксперимент с continuation worklist/memoization. Не повышать глобальный path budget одновременно с C1/C2: иначе будет потеряна причинность.

### Независимая короткая ветка: source response → storage → header

| Изменение | Минимальная проверка | Критерий приёмки/отказа | Риски и цена |
|---|---|---|---|
| **S1: Angular legacy callback** | Login возвращает source-created token; исходный `.success` пишет заданный key; следующий исходный request читает его. Парные jQuery/Angular fixtures; failure guards; два HTTP вызова рядом; затенённый `$http`; `.then` с другой формой аргумента | Токен проходит без ручной вставки проверяющим; source admin callback заполняет именно admin keys; неподдержанный callback не присоединяется по одному совпадению имени | Локальная/средняя: ошибочная привязка чужой цепочки и смешение response-data/envelope |
| **S2: actor-qualified credentials и session** | Два пользователя/роли, два набора credentials, login каждого, переключение и возврат; отсутствие admin credentials; перефразы actor; отказ 401/403 | У каждого credential/header есть правильный actor/client producer; чужой default не подставляется; alias роли согласован в state, а не только rank | Средняя: затрагивает context, actor parsing, input journal, browser namespaces |

Эти изменения можно подготовить независимо от коллекций. Показатели C1/C2 и S1/S2 нужно публиковать раздельно, затем дать результат сочетания. Успех S1 означает перенос токена выбранным callback. Он не доказывает правильность actor, совместимость пассажирского UI или весь сценарий бронирования.

### Что подготовить для приёмки без новой большой переработки

1. **Один строгий формат witness:** исходное действие и actor → выбранный event/Request → actual bound args → ответ/исключение → изменившаяся область DB/browser/bean state → следующий Request → per-step E/C/R/D. Для каждого существенного неизвестного — первая причина, а не только последняя остановка.
2. **Усилить существующий document checker:** строго различать JSON-типы, проверять wire/args/state и ожидаемые diagnostics. Не требовать механического `complete` при документированной нерелевантной неопределённости; проверять, может ли она менять заявленный результат/граф.
3. **Petclinic state probe:** сохранить нынешнюю неудачу; отделить корректировку legacy oracle от исправления formatter/effects. Требовать прежний ID, правильные поля после save и отсутствие лишней строки. Кандидат причины проверяется парной абляцией, а не объявляется уже доказанным.
4. **Реальный независимый профиль:** выбрать поддерживаемое Java/Spring-приложение другой предметной области, зафиксировать commit, исходники, конфигурацию, DB и oracle до настройки. Профиль должен содержать несколько элементов/сущностей, связанное состояние, непустые remote/data, отказ и неоднозначный вход. Старый Piggy оставить регрессионным контролем; один document fixture не считать новым holdout.

Для каждого из этих пунктов допустим честный результат «граница не пройдена»: он локализует следующую работу. Численные SLA общего score, памяти и времени здесь не выдумываются. **Предложение к согласованию для размеченных контролей:** требовать точного совпадения существенных известных значений и per-step графа на заявленном поддержанном пути, а регрессии принимать только с source-обоснованием и пересмотренным независимым ожиданием. Это локальный критерий, не обещание точности на всём Java.

## 8. Конкретное задание на следующую итерацию

> Взять неизменный № 29 как baseline. Создать отдельную копию для двух последовательных коллекционных изменений. Сначала исправить стандартный HashSet на известных строковых значениях: уникальность, результат add, размер, копирование и неизвестный порядок. Затем реализовать ограниченное доказательство no-op Map-фильтра и сохранение объектов вне возможной области записи. На одном и том же исходном Request сравнить поиск до/после, известность результата и его использование следующим запросом. Проверить независимый многозначный каталог/склад и отрицательные order/alias/throw cases. Не повышать budget и не менять NL-ranking одновременно. При следующей границе остановить расширение патча, сохранить первую потерю и принять отдельное решение. Поддержку Angular `$http.success` оформить отдельным небольшим изменением с собственной цепочкой token → storage → header; actor/credentials не объявлять исправленными этим патчем. Никаких правил по S0–S7, именам бизнес-сервисов или gold.

**Результат следующей итерации должен отвечать на два вопроса:** какие ранее известные данные теперь проходят через весь выбранный переход и какой конкретный механизм ещё препятствует продолжению. Повышение score сайта будет полезным независимым наблюдением, но не заменит эти ответы.
