# Варианты решения

**Папка вариантов нашей команды — `solutions_G/`**: нумерация своя, с 1. Пути ниже отсчитываются от корня репозитория. Общая история решений № 1–5 в `solutions/` — только для чтения и сравнения; наши файлы туда не пишутся. Пошаговая процедура (запуск) — в `solutions_G/docs/instructions.md`; проверка варианта — скилл `s0-check`, сборка посылки — скилл `submission-pack`.

## Новый вариант

1. Просмотри README вариантов нашей папки; решения № 1–5 в `solutions/` смотри как ориентир. Назначь следующий номер: максимальный номер в нашей папке плюс один, начиная с 1. Номер постоянный и не меняется при переименовании папки.
2. Создай `solutions_G/—_<feature>/`. Прочерк — символ `—`, U+2014. `<feature>` — короткое название основного изменения латиницей в нижнем регистре, слова через дефис. Пример: `—_scenario-aware-static`. При повторном подходе используй суффикс `-v2`, `-v3`; не перезаписывай существующую папку.
3. Сохрани самостоятельный снимок кода в `code/`. Общие исходные данные можно читать из `tt-challenge/`, но нельзя импортировать изменяемый код другого варианта. Не копируй весь исследуемый проект.
4. Добавь `README.md` с номером решения, названием фичи, родителем — своим вариантом из этой папки, общим из `solutions/` или «нет» для корневого варианта, — описанием изменений, командой запуска, бенчмарком и известными ограничениями.
5. Для готового варианта сохрани `submission.json` в корне и результаты проверок в `benchmark/` — их сохраняет скилл `s0-check`. Запиши SHA-256 ответа (его печатает проверка), параметры запуска и окружение. До реального запуска указывай «не измерено».

## Обязательный бенчмарк в README

Раздельно укажи:

| Показатель | Значение |
| --- | --- |
| Score сайта | — (не получен) |
| Тестовый score S0 | — (не измерен) |
| S0: executes / calls / remote / data | — |
| Формат S0–S7 | Не проверен |
| Время построения ответа | Не измерено |

После запуска заполняй показатели только по сохранённым результатам: числа берутся из отчётов проверки (скилл `s0-check`, файлы `benchmark/evaluation.json`, `format_check.json`, при сверке с родителем — `comparison.json`). Указывай, что время измерено локально, и версию Python. Округлённое значение в README допускается, полное значение сохраняй в JSON. Числа из описания организаторов не выдавай за наши измерения. S0 не является оценкой скрытых сценариев.

## Оценка сайта

Когда пользователь сообщает оценку, установи, к какому решению и `submission.json` она относится. Если это неоднозначно, спроси номер решения. Убедись, что сохранённый SHA-256 совпадает с ответом этого варианта.

Запиши полученную оценку в README и переименуй папку в `<score>_<feature>`. Например, условная оценка `0,51234` даёт имя `0.51234_scenario-aware-static`. Сохраняй точность сообщённого числа, используй точку в имени; оценка `0` тоже является полученной оценкой. Не вычисляй оценку сайта из S0 и не подставляй прогноз. При совпадении нового имени с существующей папкой не объединяй их.

Если пользователь предоставляет оценки отдельных сценариев, запиши их в `benchmark/site-score.json`, README варианта и таблицу результатов нашей папки `solutions_G/docs/results.md`. Храни общий score, S1–S7 и локальный S0 раздельно. Неизвестные значения оставляй неизвестными. Сохраняй точность отображения и источник; не дописывай предполагаемые знаки и не заменяй итог сайта средним округлённых оценок. Дополнительный завершающий ноль того же score фиксируй в метаданных без переименования папки.

Скриншот результатов сохрани без изменения в `benchmark/` и укажи его путь, дату получения и SHA-256 в `site-score.json`. Привяжи оценки к SHA-256 `submission.json` и исходного архива, если он есть (хеш архива — из `benchmark/pack.json`, его пишет скилл `submission-pack`). При дополнении метрик не пересобирай уже оценённый архив и не подменяй результаты локальной проверки оценками сайта.

Для следующего варианта используй предыдущие оценки как основу сравнения: после получения результата укажи изменения общего score и каждого доступного S1–S7, включая ухудшения. Низкие оценки помогают выбрать направления разбора, но сами по себе не доказывают причину ошибки. Исправляй общие правила анализатора; не добавляй поведение по идентификаторам сценариев или готовые рёбра под конкретный сценарий.

Если пользователь сообщил исправленную оценку того же ответа, обнови её и имя папки. Если ответ изменился, создай новый вариант с прочерком: прежняя оценка к нему не относится. Не меняй код и ответ уже оценённого варианта.

Обнови относящиеся к варианту локальные ссылки. Команды запуска делай относительными внутри варианта либо передавай пути аргументами, чтобы переименование не ломало запуск.

## Завершение

Проверь наличие README, кода, ответа и результатов проверки; сопоставь номер, обе оценки и хеш; убедись, что строка варианта есть в `solutions_G/docs/results.md`. Посылку собирай скиллом `submission-pack` после проверки и аудита. Создание варианта не означает отправку на сайт: загрузка производится только по отдельному поручению пользователя.
